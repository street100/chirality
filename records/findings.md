# Findings

Dated investigations that belong to no single arc. Row format, states and the
rules for adding, changing and retiring a row are in [[records/README]]. Prefix
is `FD`.

Every row here was a `.planning/FINDING-*.md` file, written into a gitignored
directory where a second reader could not find it. The investigation itself is
long-form and stays where it is written; the row is the part that survives a
fresh clone. `evidence:` names the investigation file **and** the live tree
spans, because the investigation is untracked and the tree is not.

⚑ Two of these investigations cite `scaffold/` paths and Python modules that the
migration evicted. Where that is so, the row says it, and the `measured:` line
carries a span in the live tree instead. A citation nobody can open is not
evidence.

### FD-14 the checkers that collect read their continuation state out of the artifact, and every checker that derives it stops at the first refusal

- state:    OPEN
- claim:    The question, for `PRB-73`: when a type checker or a typed-assembly checker refuses a term, do published implementations stop at the first refusal or collect several, and where do the systems that do both draw the line between the judgment and the instrument that measures it? **Both are published practice, and the split follows one structural fact instead of a policy preference.** A checker collects several refusals when the type of every value and the state at every block boundary is already written in the artifact under check, so a refusal costs the walk nothing. A checker whose environment is produced by the check itself takes one of three shapes: it stops at the first refusal, it is made total so that no term is ever refused, or it poisons the continuation and then suppresses what the poisoned continuation reports. `ck-instrs` threads a derived `REnv` (`lib/lowering/tal/check.chiral:225-230`, `(tck-ok env2)` feeds the next instruction), which puts this tree in the second family, and the prior art offers it three shapes. None of the three is plain collect-all with the rules unchanged.
- measured: **Fail-fast is what a specified judgment produces, in four independent specifications.** TAL states its static semantics as inference rules with no error object anywhere in them: TALTOPLAS:4744 "The purpose of the static semantics is to specify when programs are well formed" and TALTOPLAS:4746 "this is expressed by the judgment", TALTOPLAS:4753 "consists of 13 judgments". A program either has a derivation or it has none, and the specification carries no count of failing rules. CompCert is the same shape with the algorithm attached and machine-checked: the type system is a `Prop` (`wt_instr`, `wt_function`, COMPCERTRTL:170 "Record wt_function (f: function) (env: regenv): Prop :="), the checker is a function into the error monad (COMPCERTERR:45 "or [Error msg] to indicate failure.", COMPCERTERR:56 "Definition bind (A B: Type) (f: res A) (g: A -> res B) : res B :=", whose `Error` case short-circuits), and the instruction fold **explicitly keeps the first error and skips every later instruction**: COMPCERTRTL:334 "Definition type_code (e: S.typenv): res S.typenv :=" folds over `f.(fn_code)` with COMPCERTRTL:337 "| Error _ => re". That is `ck-instrs`, in a verified compiler, on purpose. The reason it can be on purpose is the correctness statement: COMPCERTRTL:580 "forall env, type_function = OK env -> wt_function f env." constrains the accept side alone, and COMPCERTRTL:757 "Theorem type_function_complete:" fixes accept against reject, so **nothing in either theorem gives a second error any verified meaning**. The JVM specifies verification as a Prolog predicate: JVMS4:12255 "A class is type safe if all its methods are type" safe, and JVMS4:12289 "predicate <code class=\"literal\">classIsTypeSafe</code> is not true, the type" then JVMS4:12290 "checker must throw the exception". A predicate holds or fails. One `VerifyError` is the whole output the specification defines. WebAssembly draws the judgment/instrument line in the document itself: WASMVALALG:7 "The specification of WebAssembly :ref:`validation <valid>` is purely *declarative*." and the appendix then WASMVALALG:10 "sketches the skeleton of a sound and complete *algorithm*" that WASMVALALG:13 "performs only a single pass over it." Its errors are bare `error_if` calls with no accumulator and no defined continuation; WASMVALALG:16 "The algorithm is expressed in typed pseudo code whose semantics is intended to be self-explanatory." is as far as the spec goes on what `error_if` does. **Collect-all is what a checker over an explicitly typed artifact produces, and both instances found are typed IRs.** LLVM's verifier accumulates: the check macro reports and returns from the enclosing check function, LLVMVERIFY:513 "/// We know that cond should be true, if not print an error message." and LLVMVERIFY:514 "#define Check(C, ...)"; `CheckFailed` sets a sticky flag, LLVMVERIFYH:179 "  void CheckFailed(const Twine &Message) {" and LLVMVERIFYH:182 "    Broken = true;"; and the walk runs to the end of the function before the flag is read, LLVMVERIFY:233 "  bool verify(const Function &F) {", LLVMVERIFY:269 "    // FIXME: We strip const here because the inst visitor strips const." and LLVMVERIFY:270 "    visit(const_cast<Function &>(F));". So LLVM is **fail-fast within one instruction and collect-all across the function**, which is exactly the granularity `enforcement/N12` needs and exactly the granularity `ck-instrs` lacks. It is affordable there because LLVM IR carries a type on every value, so a refused instruction leaves the next instruction's inputs fully typed. Cranelift is the same, and it is the one system found that **draws the line inside a single walk and documents where**: CRANEVERIFY:178 "pub struct VerifierErrors(pub Vec<VerifierError>);" is the accumulator, CRANEVERIFY:215 "    /// Report a fatal error and return `Err`." and CRANEVERIFY:221 "    /// Report a non-fatal error and return `Ok`." are the two severities, and CRANEVERIFY:165 "meaning that the verification process may continue. However, other (non-fatal)" errors are reported without stopping. The instruction loop propagates only the fatal kind (CRANEVERIFY:2128 "            for inst in self.func.layout.block_insts(block) {", CRANEVERIFY:2132 "                self.typecheck(inst, errors)?;"), and structural damage the rest of the walk depends on is fatal (CRANEVERIFY:2126 "                return errors.fatal((block, format!(\"{block} cannot be empty\")));"). The placement of type errors is stated in one comment: CRANEVERIFY:1325 "        // Typechecking instructions is never fatal", and the five type checks below it run unconditionally with their step results discarded, CRANEVERIFY:1326 "        let _ = self.typecheck_results(inst, ctrl_type, errors);". **The JVM's own answer to the derived-environment problem is to stop deriving it.** The type-checking verifier requires declared frames: JVMS4:12243 "The type checker requires a" list of stack map frames, and each frame JVMS4:12249 "specifies the verification type of each operand stack entry and of" each local at the start of each basic block. The inference verifier of JVMS4:12207 "type checking may fail even though the bytecode is in principle valid" is the older dataflow one. Making the continuation state part of the artifact is the same move LLVM and Cranelift make by typing every value. **Surface typers collect and then suppress, and both say the suppression is the point.** rustc poisons: RUSTCTYERR:303 "There is a `TyKind::Error` that is produced when the user makes a type error." with the stated intent RUSTCTYERR:305 "we would propagate this type and suppress other errors that come up due to it so as not to overwhelm" the user, guarded by RUSTCTYERR:309 "The compiler should **never** produce `Error` unless we **know** that an error has already been" reported, because RUSTCTYERR:315 "It's important to maintain this invariant because the whole point of the `Error` type is to suppress" other errors. GHC does the same at the constraint solver: GHCTCERR:327 "The cec_suppress flag says \"don't report any errors\".
