<h1 class="page-title">Strengths of <span class='sc'>Keccak</span></h1>
</div>
</header>
<div class="container">
<h1>Design and security</h1>
<p><span class='sc'>Keccak</span> follows an open design approach.</p>
<ul>
<li><span class='sc'>Keccak</span> comes with a <strong>clear design rationale</strong> and has been extensively scrutinized by <strong>third-party cryptanalysis</strong>. For more details, we refer to the <a href="third_party.html">cryptanalysis page</a>.</li>
<li>Unlike the previous hashing standards, the SHA-3, SHAKE, cSHAKE and other SHA-3-related functions are the outcome of an <strong>open competition</strong>.</li>
<li><span class='sc'>Keccak</span> has a <strong>thick safety margin</strong>. The <span class='sc'>Keccak</span> sponge function should stand by its security claim even if the number of rounds is divided by two, as we did for <a href="keyak.html"><span class='sc'>Keyak</span></a> and <a href="kangarootwelve.html"><span class='sc'>KangarooTwelve</span></a>.</li>
<li>We <a href="http://tosc.iacr.org/index.php/ToSC/article/view/597">showed</a> that the <span class='sc'>Keccak</span>-$f$ permutations have provable <strong>lower bounds on the weight of differential trails</strong>.</li>
<li>The design of the permutations follows the <strong>Matryoshka principle</strong>, where the security properties of the seven permutations are linked. The cryptanalysis of the smaller permutations, starting from the “toy” <span class='sc'>Keccak</span>-$f[25]$, is meaningful to the larger permutations, and vice-versa. In particular, differential and linear trails in one <span class='sc'>Keccak</span>-$f$ instance extend to symmetric trails in larger instances.</li>
<li>The <a href="sponge_duplex.html">sponge and duplex constructions</a> used by <span class='sc'>Keccak</span> are <strong>provably secure against generic attacks</strong>. This covers also the joint use of multiple <span class='sc'>Keccak</span> instances with different rate/capacity parameters.</li>
<li>Unlike SHA-1 and SHA-2, <span class='sc'>Keccak</span> does not have the length-extension weakness, hence <strong>does not need the HMAC nested construction</strong>. Instead, MAC computation can be performed by simply prepending the message with the key.</li>
<li>From the mode down to the round function, our design choices are fairly different from those in the SHA-1 and SHA-2 hash functions or in the Advanced Encryption Standard (AES). <span class='sc'>Keccak</span> therefore <strong>provides diversity with respect to existing standards</strong>.</li>
</ul>
<h1>Flexibility</h1>
<p><span class='sc'>Keccak</span> inherits the flexibility of the sponge and duplex constructions. It can perform quasi all symmetric cryptographic functions, from hashing to pseudo-random number generation to authenticated encryption.</p>
<ul>
<li>As a sponge function, <span class='sc'>Keccak</span> has <strong>arbitrary output length</strong>. This allows to simplify modes of use where dedicated constructions would be needed for fixed-output-length hash functions. It can be natively used for, e.g., hashing, full domain hashing, randomized hashing, stream encryption, MAC computation. In addition, the arbitrary output length makes it suitable for <a href="files/TreeHashing.pdf">tree hashing</a>.</li>
<li>As a duplex object, <span class='sc'>Keccak</span> can be used in <strong>clean and efficient modes</strong> as a <a href="files/SpongeDuplex.pdf">reseedable pseudo-random bit generator and for authenticated encryption</a>. Efficiency of duplexing comes from the <strong>absence of output transformation</strong>.</li>
<li><span class='sc'>Keccak</span> has a <strong>simple security claim</strong>. One can target a given security strength level by means of choosing the appropriate capacity, i.e., for a given capacity $c$, <span class='sc'>Keccak</span> is claimed to stand any attack up to complexity $2^{c/2}$ (unless easier generically). This is similar to the approach of <em>security strength</em> used in <a href="https://csrc.nist.gov/publications/detail/sp/800-57-part-1/rev-4/final">NIST's SP 800-57</a>.</li>
<li>The security claim is <strong>disentangled from the output length.</strong> There is a minimum output length as a consequence of the chosen security strength level (i.e., to avoid generic birthday attacks), but it is not the other way around, namely, it is not the output length that determines the security strength level. For an illustration with the classical security requirements of hashing (i.e., collision and (second) preimage resistance), we refer to our interactive page.</li>
<li>The instances in SHA-3 and SHAKE make use of a <strong>single permutation</strong> for all security strengths. This cuts down implementation costs compared to hash function families making use of two (or more) primitives, like the SHA-2 family. And with the same permutation, one can make <strong>performance-security trade-offs</strong> by way of choosing the suitable appropriate capacity-rate pair.</li>
</ul>
<h1>Implementation</h1>
<p>The <span class='sc'>Keccak</span>-<i>f</i> permutations consist of the iteration of a simple round function, similar to a block cipher without a key schedule. The choice of operations is limited to bitwise XOR, AND and NOT and rotations. There is no need for table-lookups, arithmetic operations, or data-dependent rotations.</p>
<ul>
<li><span class='sc'>Keccak</span> excels in <strong>hardware performance</strong>, with speed/area trade-offs, and outperforms SHA-2 by an order of magnitude. See for instance the works of Gürkaynak et al., <a href="https://eprint.iacr.org/2012/368">Gaj et al.</a>, Latif et al., Kavun et al., Kaps et al. and Jungk presented at the <a href="https://csrc.nist.gov/events/2012/the-third-sha-3-candidate-conference">Third SHA-3 Candidate Conference</a>.</li>
<li><span class='sc'>Keccak</span> has <strong>overall good software performance</strong>. It is on par with SHA-2 on modern processors and shines when used in a mode exploiting parallelism, such as ParallelHash (<a href="specifications.html#SP_800_185">NIST SP 800-185</a>) or <a href="kangarootwelve.html"><span class='sc'>KangarooTwelve</span></a>. On constrained platforms, <span class='sc'>Keccak</span> has <a href="https://github.com/das-labor/xbx/blob/master/documentation/benchmarking_results_may_2012.pdf">moderate code size and RAM consumption requirements</a>.</li>
<li>For modes involving a key, protecting the implementation against <strong>side-channel attacks</strong> is wanted. The operations used in <span class='sc'>Keccak</span> allow for <strong>efficient countermeasures</strong> against these attacks. Against cache-timing attacks, the most efficient implementations involve no table lookups. Against power analysis attacks and variants, <a href="files/KeccakDPA.pdf">countermeasures can take advantage of the quadratic round function</a>.</li>
</ul></div>
