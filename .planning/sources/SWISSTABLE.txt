<h1 id="swiss-tables-design-notes">Swiss Tables Design Notes</h1>

<p>Abseil provides its own family of hash tables (colloquially known as “Swiss
tables”) in place of <code class="language-plaintext highlighter-rouge">std::unordered_set</code> and <code class="language-plaintext highlighter-rouge">std::unordered_map</code>. These
classes are:</p>

<ul>
  <li><code class="language-plaintext highlighter-rouge">absl::flat_hash_map</code></li>
  <li><code class="language-plaintext highlighter-rouge">absl::flat_hash_set</code></li>
  <li><code class="language-plaintext highlighter-rouge">absl::node_hash_map</code></li>
  <li><code class="language-plaintext highlighter-rouge">absl::node_hash_set</code></li>
</ul>

<p>This design note explains how these tables were implemented, the performance
improvements our tables provide in certain cases, and why those might make you
choose them over <code class="language-plaintext highlighter-rouge">std::unordered_{set,map}</code>.</p>

<h2 id="lookup-optimizations">Lookup Optimizations</h2>

<p>Swiss tables hold a densely packed array of metadata, containing presence
information for entries in the table. This presence information allows us to
optimize both lookup and insertion operations. This metadata adds one byte of
overhead for every entry in the table.</p>

<h3 id="metadata-layout">Metadata Layout</h3>

<p>Within Swiss tables, the result of the hash function produces a 64-bit hash
value. We split this value up into two parts:</p>

<ul>
  <li>H1, a 57 bit hash value, used to identify the element index within the table
itself, which is truncated and modulated as any normal hash value would be for
lookup and insertion purposes.</li>
  <li>H2, the remaining 7 bits of the hash value, used to store metadata for this
element. The H2 hash bits are stored separately within the metadata section of
the table.</li>
</ul>

<p>For performance reasons, it is important that you use a hash function that
distributes entropy across the entire bit space well (producing an
<a href="https://en.wikipedia.org/wiki/Avalanche_effect">avalanche effect</a>). The Abseil <a href="/docs/cpp/guides/hash">hash framework</a>
accomplishes this well and should be sufficient for most users.</p>

<p><img src="images/hashbits-layout.png" align="center" style="padding:24px;display:block;margin:auto;width:75%;" /></p>

<h3 id="metadata-information">Metadata Information</h3>

<p>The metadata of a Swiss table stores presence information (whether the element
is empty, deleted, or full). Each metadata entry consists of one byte, which
consists of a single control bit and the 7 bit H2 hash. The control bit, in
combination with the value in the H2 section of the metadata, indicates whether
the associated hash element is empty, present, or has been deleted.</p>

<p><img src="images/h2-metadata.png" alt="H2 Metadata" style="padding:24px;display:block;margin:auto;width:50%;" /></p>

<p>The metadata, which is an implementation detail but can be thought of as being
laid out consecutively, maps this presence information to elements in the hash
table itself.</p>

<p><img src="images/metadata-mapping.png" alt="Metadata Relationship" style="padding:24px;display:block;margin:auto;width:100%;" /></p>

<p>In this diagram, elements with the same H1 hash are colored identically, blue
elements are empty, and black represents a deleted element.</p>

<h3 id="metadata-lookup">Metadata Lookup</h3>

<p>When searching for items in the table we use <a href="https://en.wikipedia.org/wiki/Streaming_SIMD_Extensions">SSE instructions</a> to scan for
candidate matches. The process of finding an element can be roughly summarized
as follows:</p>

<ol>
  <li>Use the H1 hash to find the start of the “bucket chain” for that hash.</li>
  <li>Use the H2 hash to construct a mask.</li>
  <li>Use SSE instructions and the mask to produce a set of candidate matches.</li>
  <li>Perform an equality check on each candidate.</li>
  <li>If no element is found amongst the current candidates, perform probing to
generate a new set of candidates. Note that a deleted element does not cease
probing, though an empty element would.</li>
</ol>

<p>Steps 2+3 can be summarized visually as:</p>

<p><img src="images/hashtable-lookup.png" alt="Metadata Lookup" style="padding:24px;display:block;margin:auto;width:85%;" /></p>

<p>Equivalent code for this lookup appears below:</p>

<div class="language-c++ highlighter-rouge"><div class="highlight"><pre class="highlight"><code><span class="n">Mask</span> <span class="nf">Match</span><span class="p">(</span><span class="n">h2_t</span> <span class="n">hash</span><span class="p">)</span> <span class="k">const</span> <span class="p">{</span>
  <span class="k">auto</span> <span class="n">match</span> <span class="o">=</span> <span class="n">_mm_set1_epi8</span><span class="p">(</span><span class="n">hash</span><span class="p">);</span>
  <span class="k">return</span> <span class="nf">Mask</span><span class="p">(</span><span class="n">_mm_movemask_epi8</span><span class="p">(</span><span class="n">_mm_cmpeq_epi8</span><span class="p">(</span><span class="n">match</span><span class="p">,</span> <span class="n">metadata</span><span class="p">)));</span>
<span class="p">}</span>
</code></pre></div></div>

<p>This process is an important performance trick. Because we can winnow 16
candidates down to only those with a matching H2 hash in only a few
instructions, we are functionally searching very deep probe chains
inexpensively.</p>

<h2 id="storage-optimizations">Storage Optimizations</h2>

<p>In addition to optimizations made in relation to element insertion and lookup,
Swiss tables were designed to also optimize certain operations that were
especially non-performant on <code class="language-plaintext highlighter-rouge">std::unordered_map</code>.</p>

<h3 id="allocation-optimizations">Allocation Optimizations</h3>

<p>In STL containers, <code class="language-plaintext highlighter-rouge">emplace()</code> will almost always:</p>

<ul>
  <li>Allocate a value_type on the heap.</li>
  <li>Try to insert the allocated entry.</li>
  <li>If the insert fails, delete the allocated entry.</li>
</ul>

<p>We avoid this allocation in all cases where the key can be inferred from the
arguments of <code class="language-plaintext highlighter-rouge">emplace()</code> without running user-defined constructors.</p>

<!---->

<div class="language-c++ highlighter-rouge"><div class="highlight"><pre class="highlight"><code><span class="n">absl</span><span class="o">::</span><span class="n">flat_hash_map</span><span class="o">&lt;</span><span class="n">int64</span><span class="p">,</span> <span class="n">std</span><span class="o">::</span><span class="n">string</span><span class="o">&gt;</span> <span class="n">m</span> <span class="o">=</span> <span class="p">{{</span><span class="mi">0</span><span class="p">,</span> <span class="s">""</span><span class="p">}};</span>
<span class="c1">// No objects of type `std::string` are constructed in the following code.</span>
<span class="n">m</span><span class="p">.</span><span class="n">emplace</span><span class="p">(</span><span class="mi">0</span><span class="p">,</span> <span class="s">"abc"</span><span class="p">);</span>
<span class="n">m</span><span class="p">.</span><span class="n">emplace</span><span class="p">(</span><span class="n">std</span><span class="o">::</span><span class="n">make_pair</span><span class="p">(</span><span class="mi">0</span><span class="p">,</span> <span class="s">"abc"</span><span class="p">));</span>
<span class="n">m</span><span class="p">.</span><span class="n">emplace</span><span class="p">(</span><span class="n">std</span><span class="o">::</span><span class="n">piecewise_construct</span><span class="p">,</span>
          <span class="n">std</span><span class="o">::</span><span class="n">forward_as_tuple</span><span class="p">(</span><span class="mi">0</span><span class="p">),</span>
          <span class="n">std</span><span class="o">::</span><span class="n">forward_as_tuple</span><span class="p">(</span><span class="s">"abc"</span><span class="p">));</span>
</code></pre></div></div>

<!---->

<p>The same optimization is applied for <code class="language-plaintext highlighter-rouge">insert()</code> operations.</p>

<h3 id="move-optimizations">Move Optimizations</h3>

<p>Similarly, we separate a hash element’s <code class="language-plaintext highlighter-rouge">value_type</code> (the type of an entry) from
its <code class="language-plaintext highlighter-rouge">init_type</code> (the type from which an entry can be constructed) to allow
insertions to consume arguments. This allows initializers to <code class="language-plaintext highlighter-rouge">std::move()</code> on
construction instead of requiring a copy.</p>

<div class="language-c++ highlighter-rouge"><div class="highlight"><pre class="highlight"><code><span class="c1">// No strings are copy-constructed in this example.</span>
<span class="c1">// std::unordered_map would have performed one string copy.</span>
<span class="n">absl</span><span class="o">::</span><span class="n">flat_hash_map</span><span class="o">&lt;</span><span class="n">string</span><span class="p">,</span> <span class="kt">int</span><span class="o">&gt;</span> <span class="n">m</span><span class="p">;</span>
<span class="n">m</span><span class="p">.</span><span class="n">insert</span><span class="p">({</span><span class="s">"hello"</span><span class="p">,</span> <span class="mi">42</span><span class="p">});</span>
</code></pre></div></div>

<p>As well, for both copy and move operations, <code class="language-plaintext highlighter-rouge">try_emplace()</code>, if the insertion
does not occur because the key already exists, will neither copy nor move
(respectively) the original elements.</p>
