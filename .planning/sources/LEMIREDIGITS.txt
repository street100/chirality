	<div class="entry-content">
		<p class="post-dateline">3 June 2021 &middot; 2 min</p>
<p>I my <a href="https://lemire.me/blog/2021/05/28/computing-the-number-of-digits-of-an-integer-quickly/">previous blog post</a>, I documented how one might proceed to compute the number of digits of an integer quickly. E.g., given the integer 999, you want 3 but given the integer 1000, you want 4. It is effectively the integer logarithm in base 10.</p>
<p>On computers, you can quickly compute the integer logarithm in base 2, and it follows that you can move from one to the other rather quickly. You just need a correction which you can implement with a table. A very good solution found in references such as Hacker&#8217;s Delight is as follows:</p>
<pre style="color: #000000; background: #ffffff;">    <span style="color: #800000; font-weight: bold;">static</span> uint32_t table<span style="color: #808030;">[</span><span style="color: #808030;">]</span> <span style="color: #808030;">=</span> <span style="color: #800080;">{</span><span style="color: #008c00;">9</span><span style="color: #808030;">,</span> <span style="color: #008c00;">99</span><span style="color: #808030;">,</span> <span style="color: #008c00;">999</span><span style="color: #808030;">,</span> <span style="color: #008c00;">9999</span><span style="color: #808030;">,</span> <span style="color: #008c00;">99999</span><span style="color: #808030;">,</span>
    <span style="color: #008c00;">999999</span><span style="color: #808030;">,</span> <span style="color: #008c00;">9999999</span><span style="color: #808030;">,</span> <span style="color: #008c00;">99999999</span><span style="color: #808030;">,</span> <span style="color: #008c00;">999999999</span><span style="color: #800080;">}</span><span style="color: #800080;">;</span>

<p>If I omit the computation of the integer logarithm in base 2, it requires just a table lookup, an addition and a shift:</p>
<pre style="color: #000000; background: #ffffff;"><span style="color: #800000; font-weight: bold;">add</span>     rax<span style="color: #808030;">,</span> <span style="color: #800000; font-weight: bold;">qword</span> <span style="color: #800000; font-weight: bold;">ptr</span> <span style="color: #808030;">[</span><span style="color: #008c00;">8</span><span style="color: #808030;">*</span>rcx <span style="color: #808030;">+</span> <span style="color: #004a43;">table</span><span style="color: #808030;">]</span>
<span style="color: #800000; font-weight: bold;">shr</span>     rax<span style="color: #808030;">,</span> <span style="color: #008c00;">32</span>
</pre>
<p>The table contains the numbers ceil(log10(2<sup>j</sup>)+1) * 2<sup>32</sup> + 2<sup>32</sup> &#8211; 10<sup>ceil(log10(2<sup>j</sup>))</sup> for j from 2 to 30, and then just ceil(log10(2<sup>j</sup>)+1) for j = 31 and j = 32. The first value is 2<sup>32</sup> .</p>
<p><a href="https://github.com/lemire/Code-used-on-Daniel-Lemire-s-blog/tree/master/2021/06/03">My implementation of Kendall&#8217;s solution is available</a>.</p>
<p><a href="https://lemire.me/blog/2025/01/07/counting-the-digits-of-64-bit-integers/">In a follow-up post</a>, I examine whether Kendall&#8217;s approach is faster. It does use fewer instructions, but whether it is actually faster is less clear. It could actually be slower in practice.</p>

            const accessedDate = this.getCurrentAccessedDate(); 

            // 3. --- NEW LOGIC: Extract ONLY the year (YYYY) ---
            // Gets the full date string, e.g., "November 23, 2025"
            const fullDateString = el.dataset.year; 
            // Use regex to find the four-digit year at the end of the string
            const match = fullDateString.match(/(\d{4})$/);
            const publicationYear = match ? match[0] : '????'; // e.g., '2025'
            
            // 4. Generate BibTeX Data with the corrected year
            const safeTitle = el.dataset.title.replace(/[^a-zA-Z0-9]/g, '').substring(0, 15);
            // Use the clean year for the BibKey
            const bibKey = (publicationYear + safeTitle); 

            const content = `@misc{${bibKey},
author = {${el.dataset.author}},
title = {{${el.dataset.title}}},
year = {${publicationYear}}, 
howpublished = {\\url{${rawUrl}}},
note = {Accessed: ${accessedDate}} }`;
            
            // 5. Show Modal
            document.getElementById('bibtex-target').textContent = content;
            modal.showModal();
        }
    };
})();

				<div class="comment-content">
					<p>I still prefer the first solution because it extends to 64 bits naturally.  The second solution can be considered a variant of the first where:<br />
* The high half of the 9*bits/32 approximation is replaced by a table lookup,<br />
* The threshold table lookup is indexed by number of bits, not number of digits (making it larger by a factor of log2(10) = 3.32), and<br />
* The threshold comparison is done in the (semantically equivalent) form of an add with carry to the low half of the table.</p>
<p>Bloating the table by a factor or 6.64 (for 32 bits, from 11<em>4 = 44 bytes to 32</em>8 = 256 bytes, or +3 cache lines) doesn&#8217;t seem like a good use of L1 cache, especially as any digit-counting function is going to be part of  some much larger output formatting code and not an inner loop by itself.</p>
<p>There&#8217;s one more trick that hasn&#8217;t shown up yet and might be useful.  Given a safe underestimate such as<br />
    y = 9*int_log2(x) / 32;<br />
then x &gt;&gt; y can be used to compute the number of digits without losing accuracy; the low digit_count(x) bits of x don&#8217;t affect the result (because 10 is a multiple of 2).</p>
<p>This <em>might</em> enable people to fit the necessary low and high parts of each table entry into a single word.</p>

<p>I believe the first one might be very slightly faster as <code>adc</code> instruction is usually a bit slower than <code>add</code>. (But really, there should be no real difference.) I tested through quick-bench.com and it seems that GCC slightly favors the first one and Clang slightly favors the second one, but I think this is unfair, since quick-bench.com does not let me to specify the architecture flag, thus it generates <code>shr eax, cl</code> instead of <code>shrx eax, edi, eax</code>, which I believe is usually a bit slower.</p>

				<div class="comment-content">
					<p>I&#8217;m late to this party, but needed a fast method in Java for determining the number of digits in a long, and came across this blog. I wanted to implement this in order to decompose long timing data ( from System.nanoTime() ) for storage and analysis in a rounded dataset. For example, if only 4 significant figures is being stored, then 123456789 is decomposed into 1.235 x 10^8, and 1235 is stored in a data structure (which could be as simple as a counter array) associated with 10^8. Knowing the exponent of an input long value is key for this operation, and of course the exponent is simply the number of decimal digits − 1. This is used for processing timing data for real-time analysis and reporting on servers handling a very large number of transactions per second, so efficiency matters.</p>
<p> I was able to build off of the ideas presented and squeeze the data needed for a long into a 64-bit table by taking advantage of the fact that 10^i is divisible by 2^i, and thus the values in the table can be shifted as x increases. This dynamic shifting does add to the number of operations required, but is still quite efficient.</p>
<p>Here&#8217;s the code if others are interested:</p>
<p>    static final long[] DIGITS_LOOKUP_TABLE =<br />
    {<br />
        0l, 1l, 3l, 7l, 11l, 27l, 59l, 142l, 167l, 359l, 774l, 1798l, 1923l,<br />
        3971l, 8990l, 19230l, 19855l, 42902l, 92054l, 190358l, 198126l, 427502l,<br />
        886254l, 1803758l, 1940902l, 4038054l, 8232358l, 17311868l, 18093118l,<br />
        36967486l, 76073580l, 159959660l, 163865910l, 331638070l, 699135004l,<br />
        1437332508l, 1456863758l, 3025912972l, 6247138444l, 12689589388l,<br />
        12982081212l, 26940724924l, 54858012348l, 110692587196l, 115376271788l,<br />
        235635356076l, 476153524652l, 981964026040l, 1006378088540l,<br />
        2037170239580l, 4153905886104l, 8551952397208l, 8674022709708l,<br />
        17470115731916l, 36162692219384l, 73546087563768l, 74156439126268l,<br />
        152226158774744l, 310555833174488l, 627215181973976l, 637985491562808l,<br />
        1306488561250616l, 2643494700626232l, 5317506979377464l<br />
    };</p>
<p>    /**<br />
     *   Determines the number of decimal digits of a non-negative long<br />
     **/<br />
    public static int digits( long x )<br />
    {<br />
        // d2 = number of digits, base 2, of x.<br />
        int d2 = 64 &#8211; Long.numberOfLeadingZeros( x );<br />
        int s = d2&gt;&gt;&gt;2;<br />
        return (int)( (DIGITS_LOOKUP_TABLE[d2]+(x&gt;&gt;&gt;s)) &gt;&gt;&gt; (d2-s) );<br />
    }</p>
<p>Note that the call to Long.numberOfLeadingZeroes() it&#8217;s handled as an intrinsic in most JVMs on most architectures, effectively making it a single machine instruction, which significantly improves performance.</p>
