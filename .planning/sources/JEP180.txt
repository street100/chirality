<p>Improve the performance of <code>java.util.HashMap</code> under high hash-collision
conditions by using balanced trees rather than linked lists to store map
entries.  Implement the same improvement in the <code>LinkedHashMap</code> class.</p>
<h2 id="Motivation">Motivation</h2>
<p>Earlier work in this area in JDK 8, namely the
<a href="http://hg.openjdk.java.net/jdk8/jdk8/jdk/rev/43bd5ee0205e">alternative string-hashing implementation</a>, improved collision
performance for string-valued keys only, and it did so at the cost of
adding a new (private) field to every <code>String</code> instance.</p>
<p>The changes proposed here will improve collision performance for any key
type that implements <code>Comparable</code>.  The alternative string-hashing
mechanism, including the private <code>hash32</code> field added to the <code>String</code>
class, can then be removed.</p>
<h2 id="Description">Description</h2>
<p>The principal idea is that once the number of items in a hash bucket
grows beyond a certain threshold, that bucket will switch from using a
linked list of entries to a balanced tree.  In the case of high hash
collisions, this will improve worst-case performance from O(n) to O(log
n).</p>
<p>This technique has already been implemented in the latest version of the
<code>java.util.concurrent.ConcurrentHashMap</code> class, which is also slated for
inclusion in JDK 8 as part of <a href="https://bugs.openjdk.org/browse/JDK-8046145">JEP 155</a>.  Portions of that code will
be re-used to implement the same idea in the <code>HashMap</code> and <code>LinkedHashMap</code>
classes.  Only the implementations will be changed; no
interfaces or specifications will be modified.  Some user-visible
behaviors, such as iteration order, will change within the bounds of
their current specifications.</p>
<p>We will not implement this technique in the legacy <code>Hashtable</code> class.
That class has been part of the platform since Java 1.0, and some legacy
code that uses it is known to depend upon iteration order.  <code>Hashtable</code>
will be reverted to its state prior to the introduction of the
alternative string-hashing implementation, and will maintain its
historical iteration order.</p>
<p>We also will not implement this technique in WeakHashMap.  An attempt was
made, but the complexity of having to account for weak keys resulted in an
unacceptable drop in microbenchmark performance.  <code>WeakHashMap</code> will also
be reverted to its prior state.</p>
<p>There is no need to implement this technique in the <code>IdentityHashMap</code>
class.  It uses <code>System.identityHashCode()</code> to generate hash codes, so
collisions are generally rare.</p>
<h2 id="Testing">Testing</h2>
<ul>
<li>Run <code>Map</code> tests from Doug Lea's JSR 166 CVS workspace (includes a couple
microbenchmarks)</li>
<li>Run performance tests of standard workloads</li>
<li>Possibly develop new microbenchmarks</li>
</ul>
<h2 id="Risks-and-Assumptions">Risks and Assumptions</h2>
<p>This change will introduce some overhead for the addition and management
of the balanced trees; we expect that overhead to be negligible.</p>
<p>This change will likely result in a change to the iteration order of the
<code>HashMap</code> class.  The <code>HashMap</code> specification
explicitly makes no guarantee  about iteration order.  The iteration order of
the <code>LinkedHashMap</code> class will be maintained.</p>
