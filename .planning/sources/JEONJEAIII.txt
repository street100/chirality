It sounds like an extremely simple problem, but it is in fact quite more complicated than one might imagine. Let us more precisely define what we want to do: we take an integer of specific bit-width and a byte buffer, and convert the input integer into a string consisting of its decimal digits, and then write it into the given buffer. For simplicity, we will assume that the integer is unsigned and is of $32$-bits. So, we want to implement the following function written in C++:</p><div class="language-cpp highlighter-rouge"><div class="highlight"><pre class="highlight"><code><span class="kt">char</span><span class="o">*</span> <span class="nf">itoa</span><span class="p">(</span><span class="n">std</span><span class="o">::</span><span class="kt">uint32_t</span> <span class="n">n</span><span class="p">,</span> <span class="kt">char</span><span class="o">*</span> <span class="n">buffer</span><span class="p">)</span> <span class="p">{</span>
  <span class="c1">// Convert n into decimal digit string and write it into buffer.</span>
  <span class="c1">// Returns the position right next to the last character written.</span>
<span class="p">}</span>
</code></pre></div></div><p>There are numerous algorithms for doing this, and I will dig into a clever algorithm invented by <a href="https://github.com/jeaiii/itoa">James Anhalt (jeaiii)</a>, which seems to be the fastest known algorithm at the point of writing this post.</p><h1 id="disclaimer">Disclaimer</h1><p>I actually have not looked (and will not look) carefully at his code (<a href="https://github.com/jeaiii/itoa/blob/main/itoa/itoa_jeaiii.cpp">MACROS</a>, oh my god 😱) and have no idea what precisely was the method of analysis he had in mind. All I write here is purely my own analysis inspired by reading <a href="https://github.com/jeaiii/itoa/blob/main/itoa/to_text_from_integer.h#L28">these lines of comment</a> he wrote:</p><div class="language-cpp highlighter-rouge"><div class="highlight"><pre class="highlight"><code><span class="c1">// 1. form a 7.32 bit fixed point numner: t = u * 2^32 / 10^log10(u)</span>
<span class="c1">// 2. convert 2 digits at a time [00, 99] by lookup from the integer portion of the fixed point number (the upper 32 bits)</span>
<span class="c1">// 3. multiply the fractional part (the lower 32 bits) by 100 and repeat until 1 or 0 digits left</span>
<span class="c1">// 4. if 1 digit left mulptipy by 10 and convert it (add '0')</span>
<span class="c1">//</span>
<span class="c1">// N == log10(u)</span>
<span class="c1">// finding N by binary search for a 32bit number N = [0, 9]</span>
<span class="c1">// this is fast and selected such 1 &amp; 2 digit numbers are faster (2 branches) than long numbers (4 branches) for the 10 cases</span>
<span class="c1">//          </span>
<span class="c1">//      /\____________</span>
<span class="c1">//     /  \______     \______</span>
<span class="c1">//    /\   \     \     \     \</span>
<span class="c1">//   0  1  /\    /\    /\    /\</span>
<span class="c1">//        2  3  4  5  6  7  8  9</span>
</code></pre></div></div><p>So it is totally possible that in fact what’s written in this post has nothing to do with what he actually did; however, I strongly believe that what I ended up with is more or less equivalent to what his code is doing, modulo some small minor differences.</p><h1 id="naïve-implementations">Naïve implementations</h1><p>The very first problem that anyone who tries to implement such a function will face is that we want to write digits from left to right, but naturally we compute the digits from right to left. Hence, unless we know the number of decimal digits in the input upfront, we do not know the exact position in the buffer that we can write our digits into. There are several different strategies to cope with this issue. Probably the simplest (and quite effective) one is to just print the digit from right to left but into a temporary buffer, and after we get all digits of $n$ we copy the temporary buffer back to the destination buffer. At the point of obtaining the left-most decimal digit of $n$, we also get the length of the string, so we know what exact bytes to copy.</p><p>With this strategy, we can think of the following implementation:</p><div class="language-cpp highlighter-rouge"><div class="highlight"><pre class="highlight"><code><span class="kt">char</span><span class="o">*</span> <span class="nf">itoa_naive</span><span class="p">(</span><span class="n">std</span><span class="o">::</span><span class="kt">uint32_t</span> <span class="n">n</span><span class="p">,</span> <span class="kt">char</span><span class="o">*</span> <span class="n">buffer</span><span class="p">)</span> <span class="p">{</span>
  <span class="kt">char</span> <span class="n">temp</span><span class="p">[</span><span class="mi">10</span><span class="p">];</span>
  <span class="kt">char</span><span class="o">*</span> <span class="n">ptr</span> <span class="o">=</span> <span class="n">temp</span> <span class="o">+</span> <span class="k">sizeof</span><span class="p">(</span><span class="n">temp</span><span class="p">)</span> <span class="o">-</span> <span class="mi">1</span><span class="p">;</span>
  <span class="k">while</span> <span class="p">(</span><span class="n">n</span> <span class="o">&gt;=</span> <span class="mi">10</span><span class="p">)</span> <span class="p">{</span>
    <span class="o">*</span><span class="n">ptr</span> <span class="o">=</span> <span class="kt">char</span><span class="p">(</span><span class="sc">'0'</span> <span class="o">+</span> <span class="p">(</span><span class="n">n</span> <span class="o">%</span> <span class="mi">10</span><span class="p">));</span>
    <span class="n">n</span> <span class="o">/=</span> <span class="mi">10</span><span class="p">;</span>
    <span class="o">--</span><span class="n">ptr</span><span class="p">;</span>
  <span class="p">}</span>
  <span class="o">*</span><span class="n">ptr</span> <span class="o">=</span> <span class="kt">char</span><span class="p">(</span><span class="sc">'0'</span> <span class="o">+</span> <span class="n">n</span><span class="p">);</span>
  <span class="k">auto</span> <span class="n">length</span> <span class="o">=</span> <span class="n">temp</span> <span class="o">+</span> <span class="k">sizeof</span><span class="p">(</span><span class="n">temp</span><span class="p">)</span> <span class="o">-</span> <span class="n">ptr</span><span class="p">;</span>
  <span class="n">std</span><span class="o">::</span><span class="n">memcpy</span><span class="p">(</span><span class="n">buffer</span><span class="p">,</span> <span class="n">ptr</span><span class="p">,</span> <span class="n">length</span><span class="p">);</span>
  <span class="k">return</span> <span class="n">buffer</span> <span class="o">+</span> <span class="n">length</span><span class="p">;</span>
<span class="p">}</span>
</code></pre></div></div><p>(Demo: <a href="https://godbolt.org/z/7G7ecs7r4">https://godbolt.org/z/7G7ecs7r4</a>)</p><p>The size of the temporary buffer is set to $10$, because that’s the maximum possible decimal length for <code class="language-plaintext highlighter-rouge">std::uint32_t</code>.</p><p>The mismatch between the order of computation and the order of desired output is indeed a quite nasty problem, but let us forget about this issue for a while because there is something more interesting to say here.</p><p>There are several performance issues in this code, and one of them is the division by $10$. Of course, since the divisor is a known constant, our lovely compiler will automatically convert the division into multiply-and-shift (see <a href="https://gmplib.org/~tege/divcnst-pldi94.pdf">this classic paper</a> for example), so we do not need to worry about the dreaded <code class="language-plaintext highlighter-rouge">idiv</code> instruction which is extremely infamous of its performance. However, for simple enough algorithms like this, multiplication can still be a performance killer, so it is reasonable to expect that we will get a better performance by reducing the number of multiplications.</p><p>Regarding this, Andrei Alexandrescu popularized the idea of generating two digits per a division, so halving the required number of multiplications. Note that we need to compute both the quotient and the remainder, and as far as I know at least $2$ multiplications should be performed to get both of them and there is no way to do it with just one multiplication. Hence, for each pair of $2$ digits, we need to perform $2$ multiplications, thus for integers with $10$ digits we need $8$ multiplications, since we need $4$ divisions to separate $5$ pairs of $2$ digits.</p><p>Quite surprisingly, in fact we can almost halve that number again into $5$, which (I believe) is the core benefit of James Anhalt’s algorithm. The crux of the idea can be summarized as follows: given $n$, we find an integer $y$ satisfying</p>\[n = \left\lfloor\frac{10^{k}y}{2^{D}}\right\rfloor\]<p>for some nonnegative integer constants $k$ and $D$.</p><p>This transformation is a real deal, because after we get such $y$, we can extract $2$ digits of $n$ per a multiplication. To see how, recall that in general</p>\[\left\lfloor\frac{a}{bc}\right\rfloor =\left\lfloor\frac{\lfloor a/b \rfloor}{c}\right\rfloor\]<p>holds for any positive integers $a,b,c$; that is, dividing $a$ by $bc$ is equivalent to dividing $a$ by $b$ first and then by $c$. Therefore, for any $l\leq k$, we have</p>\[\left\lfloor\frac{10^{k-l}y}{2^{D}}\right\rfloor = \left\lfloor\frac{n}{10^{l}}\right\rfloor.\]<p>So, for example, let $k=l=8$, then</p>\[\left\lfloor\frac{n}{10^{8}}\right\rfloor = \left\lfloor\frac{y}{2^{D}}\right\rfloor.\]<p>Assuming that $n$ is of $10$ digits, the left-hand side is precisely the first $2$ digits of $n$, while the right-hand side is just the right-shift of $y$ by $D$-bits.</p><p>On the other hand, the next $2$ digits of $n$ can be computed as</p>\[\left(\left\lfloor\frac{n}{10^{6}}\right\rfloor \ \operatorname{mod}\ 10^{2}\right) = \left(\left\lfloor\frac{10^{2}y}{2^{D}}\right\rfloor \ \operatorname{mod}\ 10^{2}\right).\]<p>Note that, if we write $y$ as $y=2^{D}q + r$ where $q$ is the quotient and $r$ is the remainder, then</p>\[10^{2}y = 2^{D}(10^{2}q) + 10^{2}r,\]<p>so</p>\[\left(\left\lfloor\frac{10^{2}y}{2^{D}}\right\rfloor \ \operatorname{mod}\ 10^{2}\right) = \left(\left(10^{2}q + \left\lfloor\frac{10^{2}r}{2^{D}}\right\rfloor\right) \ \operatorname{mod}\ 10^{2}\right) = \left(\left\lfloor\frac{10^{2}r}{2^{D}}\right\rfloor \ \operatorname{mod}\ 10^{2}\right).\]<p>Also, since $r&lt;2^{D}$, $\left\lfloor\frac{10^{2}r}{2^{D}}\right\rfloor$ is strictly less than $10^{2}$, so we get</p>\[\left(\left\lfloor\frac{n}{10^{6}}\right\rfloor \ \operatorname{mod}\ 10^{2}\right) = \left\lfloor\frac{10^{2}r}{2^{D}}\right\rfloor.\]<p>This means that, in order to compute the next $2$ digits of $n$, we first obtain the remainder of $y$ divided by $2^{D}$, and then multiply $10^{2}$ to it, and then obtain the quotient of it divided by $2^{D}$. In other words, we just need to first obtain the lowest $D$-bits, multiply $10^{2}$ to it, and then right-shift the result by $D$-bits. As you can see, we only need $1$ multiplication here.</p><p>This trend continues: to compute the next $2$ digits of $n$, we only need to obtain the lowest $D$-bits, multiply $10^{2}$, and then right-shift the result by $D$-bits, so in particular we only need $1$ multiplication for generating each pair of $2$ digits. Indeed, it can be inductively shown that if we write $y_{0}=y$ and $y_{i+1} = 10^{2}(y_{i}\ \operatorname{mod}\ 2^{D})$, then</p>\[\left(\left\lfloor\frac{n}{10^{k-2i}}\right\rfloor \ \operatorname{mod}\ 10^{2}\right) = \left\lfloor\frac{y_{i}}{2^{D}}\right\rfloor\]<p>holds for each $i=0,1,2,3,4$.</p><h2 id="how-to-compute-y">How to compute $y$?</h2><p>Alright, so we get that having $y$ satisfying</p>\[n = \left\lfloor\frac{10^{k}y}{2^{D}}\right\rfloor\]<p>is pretty useful for our purpose. The next question is how to find such $y$. Note that the above equality is equivalent to the inequality</p>\[n \leq \frac{10^{k}y}{2^{D}} &lt; n+1,\]<p>or</p>\[\tag{$*$} \frac{2^{D}n}{10^{k}} \leq y &lt; \frac{2^{D}(n+1)}{10^{k}}.\]<p>Assuming $2^{D}\geq 10^{k}$, $y=\left\lceil\frac{2^{D}n}{10^{k}}\right\rceil$ will obviously do the job, but computing $\left\lceil\frac{2^{D}n}{10^{k}}\right\rceil$ might be nontrivial. Hence, let us first try something easier:</p>\[y = n\left\lceil\frac{2^{D}}{10^{k}}\right\rceil.\]<p>Here, $\left\lceil\frac{2^{D}}{10^{k}}\right\rceil$ is just a constant and is not dependent on $n$, so computing $y$ is just a single integer multiplication.</p><p>With $k=8$ and $n&lt;2^{32}$, we can show that this $y$ always satisfies $(*)$ if we take $D\geq 57$; we just need to find the smallest $D$ satisfying $(2^{32}-1)\left(\left\lceil\frac{2^{D}}{10^{k}}\right\rceil - \frac{2^{D}}{10^{k}}\right) &lt; \frac{2^{D}}{10^{k}}$. However, it seems that such a refactoring causes the code to perform worse, probably because the number of additions performed is increased. Nevertheless, that is also one viable option, especially regarding the code size.</p><h1 id="better-choices-for-y">Better choices for $y$</h1><p>The above code is pretty good for $n$’s up to $6$ digits, but not so much for longer $n$’s, as we have to perform masking in addition to multiplication and shift for each $2$ digits. This is due to $D$ being not equal to $32$, so it will be beneficial if we can choose $D=32$ even for $n$’s with digits more than $6$. And it turns out that we can.</p><p>The reason we had to choose $D&gt;32$ was due to our poor choice of $y$:</p>\[y = n\left\lceil\frac{2^{D}}{10^{k}}\right\rceil.\]<p>Recall that we do not need to choose $y$ like this; all we need to ensure is that $y$ satisfies the inequality</p>\[\tag{$*$} \frac{2^{D}n}{10^{k}} \leq y &lt; \frac{2^{D}(n+1)}{10^{k}}.\]<p>Slightly generalizing what we have done, let us suppose that we want to obtain $y$ by computing</p>\[y = \left\lfloor\frac{nm}{2^{L}}\right\rfloor\]<p>for some positive integer constants $m$ and $L$. Then the inequality $(*)$ can be rewritten as</p>\[\tag{$**$} \frac{1}{n}\left\lceil\frac{2^{D}n}{10^{k}}\right\rceil \leq \frac{m}{2^{L}} &lt; \frac{1}{n}\left\lceil\frac{2^{D}(n+1)}{10^{k}}\right\rceil.\]<p>At the time of writing this post, I am not quite sure if there is an elegant way to obtain the precise admissible range of $m$ and $L$ for the above inequality with any given range of $n$, but a reasonable guess is that</p>\[m = \left\lceil\frac{2^{D+L}}{10^{k}}\right\rceil + 1\]<p>will often do the job. Indeed, in this case we have</p>\[\frac{mn}{2^{L}} \geq \frac{2^{D}n}{10^{k}} + \frac{n}{2^{L}},\]<p>so the left-hand side of \((**)\) is always satisfied if</p>\[2^{L} \leq n\]<p>holds for all $n$ in the range. On the other hand, we have</p>\[\frac{mn}{2^{L}} &lt; \frac{2^{D}n}{10^{k}} + \frac{n}{2^{L-1}},\]<p>so the right-hand side of \((**)\) is always satisfied if</p>\[\frac{n}{2^{L-1}}\leq \frac{2^{D}}{10^{k}},\]<p>or equivalently,</p>\[\frac{10^{k}n}{2^{D-1}} \leq 2^{L}\]<p>holds for all $n$ in the range.</p><p>Thus for example, when $n$ is of $7$ or $8$ digits (so $n\in[10^{6}, 10^{8}-1]$), $k=6$, and $D=32$, it is enough to have</p>\[\frac{10^{6}(10^{8} - 1)}{2^{31}} \leq 2^{L} \leq 10^{6},\]<p>which is equivalent to</p>\[16 \leq L \leq 19.\]<p>Hence, we take $L = 16$ and accordingly $m = 281474978$. Of course, since $m$ is even we can equivalently take $L = 15$ and $m = 140737489$ as well, so this method of analysis is clearly far from being tight.</p><p>(In fact, it can be exhaustively verified that the left-hand side of $(*)$ is maximized when $n=1000795$, while the right-hand side is minimized when $n=10^{8}-1$, which together yield the inequality</p>\[\frac{4298381796}{1000795} \leq \frac{m}{2^{L}} &lt; \frac{429496729600}{99999999}.\]<p>The minimum $L$ allowing an integer solution for $m$ to the above inequality is $L=15$ and in this case $m = 140737489$ is the unique solution.)</p><p>When $n$ is of $9$ or $10$ digits, a similar analysis does not give the best result, especially for $10$ digits it fails to give any admissible choice of $L$ and $m$. Well, compared to <code class="language-plaintext highlighter-rouge">itoa_var_length_naive</code>, the performance benefit of <code class="language-plaintext highlighter-rouge">itoa_better_y</code> seems not very impressive to be honest. Nevertheless, I still think the idea behind the algorithm is pretty intriguing.</p><h1 id="back-to-fixed-length-case">Back to fixed-length case</h1><p>So far we only have looked at the case of $32$-bit unsigned integers. For $64$-bit integers, what people typically do is to first divide the input number into several segments of $32$-bit integers, and then print them using methods for $32$-bit integers. In this case, typically only the first segment is of variable length and remaining segments are of fixed length. As we can see in the benchmark above, when the length is known we can do a lot better. For simplicity of the following discussion, let us suppose that the input integer is at most of $9$ digits and we want to always print $9$ digits with possible leading zeros.</p><p>While what we have done in <code class="language-plaintext highlighter-rouge">itoa_always_10_digits</code> is not so bad, we can certainly do better by choosing $D=32$ which eliminates the need for performing masking at each generation of $2$ digits. Recall that all we need to do is to find an integer $y$ satisfying</p>\[\tag{$*$} \frac{2^{D}n}{10^{k}} \leq y &lt; \frac{2^{D}(n+1)}{10^{k}}\]<p>for given $n$. Since we want to always print $9$ digits, we take $k=8$. What’s different from the previous case is that now $n$ can be any integer in the range $[1,10^{9}-1]$ (ignoring $n=0$ case, but that is not a big deal), in particular it can be very small. In this case, one can show by exhaustively checking all possible $n$’s that the inequality</p>\[\tag{$**$} \frac{1}{n}\left\lceil\frac{2^{D}n}{10^{k}}\right\rceil \leq \frac{m}{2^{L}} &lt; \frac{1}{n}\left\lceil\frac{2^{D}(n+1)}{10^{k}}\right\rceil\]<p>does not have a solution, because the maximum value of the left-hand side is bigger than the minimum value of the right-hand side. Therefore, it is not possible to compute $y$ by just performing a multiplication followed by a shift.</p><p>Instead, we choose</p>\[y = \left\lfloor \frac{nm}{2^{L}} \right\rfloor + 1,\]<p>which means that we indeed omit masking at each generation of $2$ digits, but at the cost of additionally performing an increment for the initial step of computing $y$.</p><p>With this choice of $y$, $(*)$ becomes</p>\[\tag{$**'$} \frac{1}{n}\left\lceil\frac{2^{D}n}{10^{k}}\right\rceil - \frac{1}{n} \leq \frac{m}{2^{L}} &lt; \frac{1}{n}\left\lceil\frac{2^{D}(n+1)}{10^{k}}\right\rceil - \frac{1}{n}\]<p>instead of $(**)$. Then we can perform a similar analysis to conclude that $L = 25$ with</p>\[m = \left\lceil \frac{2^{D+L}}{10^{k}} \right\rceil = 1441151881\]<p>do the job. In fact, an exhaustive check shows that we can even take $L = 24$ and $m = 720575941$.</p><p>EDIT: Recall that in the above, the range of $n$ is constrained into $[0,10^{9}-1]$. It turns out $L = 24$ with $m = 720575941$ works only up to $n = 1133989877$, and it starts to produce errors if $n \geq 1133989878$.</p><p>I derived a better, but still incomplete analysis <a href="https://jk-jeon.github.io/posts/2022/12/fixed-precision-formatting/#appendix-fixed-point-fraction-trick-revisited">here</a>. After a while, I eventually obtained a complete algorithm for computing the optimal bounds, and wrote a <a href="https://github.com/jk-jeon/idiv/blob/main/subproject/example/jeaiii_analysis.cpp">program</a> that does the analysis. The algorithm itself is not published anywhere at this moment.</p><h1 id="concluding-remarks">Concluding remarks</h1><p>I applied a minor variation of the algorithm explained here into my <a href="https://github.com/jk-jeon/dragonbox/blob/master/source/dragonbox_to_chars.cpp">Dragonbox implementation</a> to speed up digit generation, and the result was quite satisfactory. I think probably the complete branching for all possible lengths of the input is not a brilliant idea for generic applications, but the idea of coming up with $y$ that enables generating each pair of $2$ digits by only performing a multiply-and-shift is very clever and useful. I expect that this same trick might be applicable to other problems as well, fixed-precision floating-point formatting for example.</p></section><footer class="page__meta"><p class="page__taxonomy">
