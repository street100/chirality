      <h1 class="docChapterTitle" data-parent="Part IV: Image Effects">Chapter 25. Rendering Vector Art on the GPU</h1>

      <p><em>Charles Loop<br>
        Microsoft Research</em></p>

      <p><em>Jim Blinn<br>
        Microsoft Research</em></p>

      <h2>25.1 Introduction</h2>

      <p>Vector representations are a resolution-independent means of specifying shape. They have the advantage that at
        any scale, content can be displayed without tessellation or sampling artifacts. This is in stark contrast to a
        raster representation consisting of an array of color values. Raster images quickly show artifacts under scale
        or perspective mappings. Our goal in this chapter is to present a method for accelerating the rendering of
        vector representations on the GPU.</p>

      <p>Modern graphics processing units excel at rendering triangles and triangular approximations to smooth objects.
        It is somewhat surprising to realize that the same architecture is ideally suited to rendering smooth
        vector-based objects as well. A vector object contains layers of closed paths and curves. These paths and curves
        are generally quadratic and cubic Bézier spline curves, emitted by a drawing program. We present algorithms for
        rendering these spline curves directly in terms of their mathematical descriptions, so that they are resolution
        independent and have a minimal geometric representation.</p>

      <p>The main ingredient of our algorithm is the notion of <em>implicitization</em>: the transformation from a
        parametric [<em>x</em>(<em>t</em>) <em>y</em>(<em>t</em>)] to implicit <em>f</em> (<em>x</em>, <em>y</em>) = 0
        plane curve. We render the convex hull of the Bézier control points as polygons, and a pixel shader program
        determines pixel inclusion by evaluating the curve's implicit form. This process becomes highly efficient by
        leveraging GPU interpolation functionality and choosing just the right implicit form. In addition to resolving
        in/out queries at pixels, we demonstrate a mechanism for performing antialiasing on these curves using hardware
        gradients. Much of this work originally appeared in Loop and Blinn 2005.</p>

      <h2>25.2 Quadratic Splines</h2>

      <p>The best way to understand our algorithm is to show how it works with a simple example. Consider the letter "e"
        shown in <a href="javascript:popUp('elementLinks/25fig01.jpg')">Figure 25-1</a>.
        <a href="javascript:popUp('elementLinks/25fig01.jpg')">Figure 25-1a</a> shows the TrueType data used to describe
        this font glyph. TrueType uses a combination of quadratic B-splines and line segments to specify an oriented
        vector outline. The region on the right0hand side of the curve is considered inside by convention. The hollow
        dots are B-spline control points that define curves; the solid dots are points on the curve that can define
        discontinuities such as sharp corners. As a preprocess, we convert the B-spline representation to Bézier form by
        inserting new points at the midpoint of adjacent B-spline control points. Each B-spline control point will
        correspond to a quadratic Bézier curve. Next, we triangulate the interior of the closed path and form a triangle
        for each quadratic Bézier curve. After triangulation, we will have interior triangles (shown in green) and
        boundary triangles that contain curves (shown in red and blue), as you can see in
        <a href="javascript:popUp('elementLinks/25fig01.jpg')">Figure 25-1b</a>.</p>

      <div class="figure">
        <a href="javascript:popUp('elementLinks/25fig01.jpg')"><img src="https://developer.download.nvidia.com/books/gpugems3/25fig01.jpg" alt="25fig01.jpg"></a>
        <p><a href="javascript:popUp('elementLinks/25fig01.jpg')">Figure 25-1</a> Rendering Quadratic Splines</p>
      </div>

      <p>The interior triangles are filled and rendered normally. Triangles that contain curves are either convex or
        concave, depending on which side of the curve is inside the closed region. See the red and blue curves in
        <a href="javascript:popUp('elementLinks/25fig01.jpg')">Figure 25-1b</a>.</p>

      <p>We use a shader program to determine if pixels are on the inside or outside of a closed region. Before getting
        to this shader, we must assign [<em>u v</em>] coordinates to the vertices of the triangles that contain curves.
        An example is shown in <a href="javascript:popUp('elementLinks/25fig02.jpg')">Figure 25-2</a>. When these
        triangles are rendered under an arbitrary 3D projective transform, the GPU will perform perspective-correct
        interpolation of these coordinates and provide the resulting [<em>uv</em>] values to a pixel shader program.
        Instead of looking up a color value as in texture mapping, we use the [<em>u v</em>] coordinate to evaluate a
        procedural texture. The pixel shader computes the expression</p>

      <table>
        <tbody>
        <tr>
          <td>
            <p><em>u</em> <sup>2</sup> - <em>v</em>,</p>
          </td>
        </tr>
        </tbody>
      </table>

      <div class="figure">
        <a href="javascript:popUp('elementLinks/25fig02.jpg')"><img src="https://developer.download.nvidia.com/books/gpugems3/25fig02.jpg" alt="25fig02.jpg"></a>
        <p><a href="javascript:popUp('elementLinks/25fig02.jpg')">Figure 25-2</a> Procedural Texture Coordinate
          Assignment</p>
      </div>

      <p>using the sign of the result to determine pixel inclusion. For convex curves, a positive result means the pixel
        is outside the curve; otherwise it is inside. For concave curves, this test is reversed.</p>

      <p>The size of the resulting representation is proportional to the size of the boundary curve description. The
        resulting image is free of any artifacts caused by tessellation or undersampling because all the pixel centers
        that lie under the curved region are colored and no more.</p>

      <p>The intuition behind why this algorithm works is as follows. The procedural texture coordinates [0 0], [½ 0],
        and [1 1] (as shown in <a href="javascript:popUp('elementLinks/25fig02.jpg')">Figure 25-2</a>) are themselves
        Bézier control points of the curve</p>

      <table>
        <tbody>
        <tr>
          <td>
            <p><em>u</em>(<em>t</em>) = <em>t</em>,</p>
          </td>

          <td>
            <p><em>v</em>(<em>t</em>) = <em>t</em> <sup>2</sup>.</p>
          </td>
        </tr>
        </tbody>
      </table>

      <p>This is clearly a parameterization for the algebraic (implicit) curve <em>u</em> <sup>2</sup> - <em>v</em> = 0.
        Suppose <strong>P</strong> is the composite transform from <em>u</em>, <em>v</em> space to curve design (glyph)
        space to viewing and perspective space to screen space. Ultimately this will be a projective mapping from 2D
        onto 2D. Any quadratic curve segment projected to screen space will have such a <strong>P</strong>. When the GPU
        interpolates the texture coordinates, it is in effect computing the value of P<sup>-1</sup> for each pixel.
        Therefore, we can resolve the inside/outside test in <em>u</em>, <em>v</em> space where the implicit equation is
        simple, needing only one multiply and one add.</p>

      <p>As an alternative, we could find the algebraic equation of each curve segment in screen space. However, this
        would require dozens of arithmetic operations to compute the general second-order algebraic curve coefficients
        and require many operations to evaluate in the corresponding pixel shader. Furthermore, the coefficients of this
        curve will change as the viewing transform changes, requiring recomputation. Our approach requires no such
        per-frame processing, other than the interpolation of [<em>u v</em>] procedural texture coordinates done by the
        GPU.</p>

      <p>Quadratic curves turn out to be a very simple special case. Assignment of the procedural texture coordinates is
        the same for all (integral) quadratic curves, and the shader equation is simple and compact. However, drawing
        packages that produce vector artwork often use more-flexible and smooth cubic splines. Next, we extend our
        rendering algorithm to handle cubic curves. The good news is that the runtime shader equation is also simple and
        compact. The bad news is that the preprocessing—assignment of procedural texture coordinates—is nontrivial.</p>

      <h2>25.3 Cubic Splines</h2>

      <p>Our algorithm for rendering cubic spline curves is similar in spirit to the one for rendering quadratic curves.
        An oriented closed path is defined by cubic Bézier curve segments, each consisting of four control points. See
        <a href="javascript:popUp('elementLinks/25fig03.jpg')">Figure 25-3a</a>. We assume the right-hand side of the
        curve to be considered inside. The convex hull of these control points forms either a quadrilateral consisting
        of two triangles, or a single triangle. As before, we triangulate the interior of the path, as shown in
        <a href="javascript:popUp('elementLinks/25fig03.jpg')">Figure 25-3b</a>. The interior triangles are filled and
        rendered normally. The interesting part is how to generalize the procedural texture technique we used for
        quadratics.</p>

      <div class="figure">
        <a href="javascript:popUp('elementLinks/25fig03.jpg')"><img src="https://developer.download.nvidia.com/books/gpugems3/25fig03.jpg" alt="25fig03.jpg"></a>
        <p><a href="javascript:popUp('elementLinks/25fig03.jpg')">Figure 25-3</a> Rendering Cubic Splines</p>
      </div>

      <p>Unlike parametric quadratic curves, parametric cubic plane curves are not all projectively equivalent. That is,
        there is no single proto-curve that all others can be projected from. It is well known that all rational
        parametric plane curves have a corresponding algebraic curve of the same degree. It turns out that the algebraic
        form of a parametric cubic belongs to one of three projective types (Blinn 2003), as shown in
        <a href="javascript:popUp('elementLinks/25fig04.jpg')">Figure 25-4</a>. Any arbitrary cubic curve can be
        classified as a serpentine, cusp, or loop. Furthermore, a projective mapping exists that will transform an
        arbitrary parametric cubic curve onto one of these three curves. If we map the Bézier control points of the
        curve under this transform, we will get a Bézier parameterization of some segment of one of these three curves.
      </p>

      <div class="figure">
        <a href="javascript:popUp('elementLinks/25fig04.jpg')"><img src="https://developer.download.nvidia.com/books/gpugems3/25fig04.jpg" alt="25fig04.jpg"></a>
        <p><a href="javascript:popUp('elementLinks/25fig04.jpg')">Figure 25-4</a> All Parametric Cubic Plane Curves Can
          Be Classified as the Parameterization of Some Segment of One of These Three Curve Types</p>
      </div>

      <p>A very old result (Salmon 1852) on cubic curves states that all three types of cubic curves will have an
        algebraic representation that can be written</p>

      <table>
        <tbody>
        <tr>
          <td>
            <p><em>k</em> <sup>3</sup> - <em>lmn</em> = 0,</p>
          </td>
        </tr>
        </tbody>
      </table>

      <p>where <em>k</em>, <em>l</em>, <em>m</em>, and <em>n</em> are linear functionals corresponding to lines
        <strong>k</strong>, <strong>l</strong>, <strong>m</strong>, and <strong>n</strong> as in
        <a href="javascript:popUp('elementLinks/25fig04.jpg')">Figure 25-4</a>. (The reason line <strong>n</strong> does
        not appear in <a href="javascript:popUp('elementLinks/25fig04.jpg')">Figure 25-4</a> will be made clear
        shortly.) More specifically, <em>k</em> = <em>au</em> + <em>bv</em> + <em>cw</em>, where [<em>u v w</em>] are
        the homogeneous coordinates of a point in the plane, and <strong>k</strong> = [<em>a b c</em>]
        <em><sup>T</sup></em> are the coordinates of a line; and similarly for <em>l</em>, <em>m</em>, and <em>n</em>.
        The relationship of the lines <strong>k</strong>, <strong>l</strong>, <strong>m</strong>, and <strong>n</strong>
        to the curve <strong>C</strong>(<em>s</em>, <em>t</em>) has important geometric significance. A serpentine curve
        has inflection points at <strong>k</strong>
        <img src="https://developer.download.nvidia.com/books/gpugems3/U2229.GIF" class="articleIcon" alt="U2229.GIF">
        <strong>l</strong>, <strong>k</strong>
        <img src="https://developer.download.nvidia.com/books/gpugems3/U2229.GIF" class="articleIcon" alt="U2229.GIF">
        <strong>m</strong>, and <strong>k</strong>
        <img src="https://developer.download.nvidia.com/books/gpugems3/U2229.GIF" class="articleIcon" alt="U2229.GIF">
        <strong>n</strong> and is tangent to lines <strong>l</strong>, <strong>m</strong>, and <strong>n</strong>,
        respectively. A loop curve has a double point at <strong>k</strong>
        <img src="https://developer.download.nvidia.com/books/gpugems3/U2229.GIF" class="articleIcon" alt="U2229.GIF">
        <strong>l</strong> and <strong>k</strong>
        <img src="https://developer.download.nvidia.com/books/gpugems3/U2229.GIF" class="articleIcon" alt="U2229.GIF">
        <strong>m</strong> and is tangent to lines <strong>l</strong> and <strong>m</strong> at this point;
        <strong>k</strong>
        <img src="https://developer.download.nvidia.com/books/gpugems3/U2229.GIF" class="articleIcon" alt="U2229.GIF">
        <strong>n</strong> corresponds to an inflection point. A cusp curve has a cusp at the point where coincident
        lines <strong>l</strong> and <strong>m</strong> intersect <strong>k</strong>, and it is tangent to line
        <strong>l</strong> = <strong>m</strong> at this point; and <strong>k</strong>
        <img src="https://developer.download.nvidia.com/books/gpugems3/U2229.GIF" class="articleIcon" alt="U2229.GIF">
        <strong>n</strong> corresponds to an inflection point.</p>

      <p>The procedural texture coordinates are the values of the <em>k</em>, <em>l</em>, <em>m</em>, and <em>n</em>
        functionals at each cubic Bézier control point. When the (triangulated) Bézier convex hull is rendered, these
        coordinates are interpolated by the GPU and a pixel shader program is called that evaluates the shader equation
        <em>k</em> <sup>3</sup> - <em>lmn</em>. This will determine if a pixel is inside or outside the curve based on
        the sign of the result.</p>

      <p>We work in homogeneous coordinates where points in the plane are represented by 3-tuples [<em>x y w</em>]; the
        2D Cartesian coordinates are <em>x</em>/<em>w</em> and <em>y</em>/<em>w</em>. We also work with a homogeneous
        curve parameterization where the parameter value is represented by the pair [<em>s t</em>]; the 1D scalar
        parameter is <em>s</em>/<em>t</em>. We use homogeneous representations because the projective geometric notion
        of points at infinity is captured by <em>w</em> = 0; similarly, an infinite parameter value occurs when
        <em>t</em> = 0.</p>

      <p>In principle, we can render any planar cubic Bézier curve defined this way; however, we make some simplifying
        assumptions to ease the derivation and implementation of our algorithm. The first is that the Bézier control
        points are affine, so <em>w</em> = 1. This means that curves must be integral as opposed to rational. This is
        not a severe limitation, because most drawing tools support only integral curves. We will still be able to
        render the correct projected image of an integral cubic plane curve, but in the plane where the curve is defined
        it cannot be rational. For integral curves the line <strong>n</strong> = [0 0 1]; that is, the line at infinity.
        All three cubic proto-curves in <a href="javascript:popUp('elementLinks/25fig04.jpg')">Figure 25-4</a> have
        integral representations, so line <strong>n</strong> does not appear. The linear functional corresponding to the
        line at infinity is <em>n</em> = 1, so the shader equation simplifies to</p>

      <table>
        <tbody>
        <tr>
          <td>
            <p><em>k</em> <sup>3</sup> - <em>lm</em>.</p>
          </td>
        </tr>
        </tbody>
      </table>

      <p>Although this saves only one multiply in the shader, it removes an entire texture coordinate from a vertex,
        leading to potentially more-efficient code. The primary reason for assuming integral curves, however, is to
        simplify curve classification. Our second assumption is that the control point coordinates are exact
        floating-point numbers. This assumption is not strictly necessary, but we can avoid floating-point round-off
        errors that might crop up in tests for equality. This corresponds to an interactive drawing scenario where
        control points lie on a regular grid.</p>

      <p>A cubic Bézier curve in homogeneous parametric form is written</p>

      <p><img src="https://developer.download.nvidia.com/books/gpugems3/0549equ01.jpg" alt="0549equ01.jpg"></p>

      <p>where the <strong>b</strong> <em><sub>i</sub></em> are cubic Bézier control points.</p>

        correspond to inflection points of <strong>C</strong>(<em>s</em>, <em>t</em>). An inflection point is where the
        curve changes its bending direction, defined mathematically as parameter values where the first and second
        derivatives of <strong>C</strong>(<em>s</em>, <em>t</em>) are linearly dependent. The derivation of the function
        <em>I</em> is not needed for our current purposes; see Blinn 2003 for a thorough discussion. For integral cubic
        curves,</p>

      <h2>25.4 Triangulation</h2>

      <p>Our triangulation procedure was only briefly discussed in Sections 25.2 and 25.3 in the interest of simplicity.
        An important detail not previously mentioned is that Bézier convex hulls cannot overlap. There are two reasons
        for this: one is that overlapping triangles cause problems for triangulation code; the other is that unwanted
        portions of one filled region might show through to the other, resulting in a visual artifact. This problem can
        be resolved by subdividing one of the offending curves so that Bézier curve convex hulls no longer overlap, as
        shown in <a href="javascript:popUp('elementLinks/25fig06.jpg')">Figure 25-6</a>.</p>

      <div class="figure">
        <a href="javascript:popUp('elementLinks/25fig06.jpg')"><img src="https://developer.download.nvidia.com/books/gpugems3/25fig06.jpg" alt="25fig06.jpg"></a>
        <p><a href="javascript:popUp('elementLinks/25fig06.jpg')">Figure 25-6</a> Handling Overlapping Triangles</p>
      </div>

      <p>We locally triangulate all non-overlapping Bézier convex hulls. For quadratics, the Bézier convex hull is
        uniquely a triangle. For cubics, the Bézier convex hull may be a quad or a triangle. If it is a quad, we
        triangulate by choosing either diagonal. Next, the interior of the entire boundary is triangulated. The details
        of this procedure are beyond the scope of this chapter. Any triangulation procedure for a multicontour polygon
        will work.</p>

      <p>Recently, Kokojima et al. 2006 presented a variant on our approach for quadratic splines that used the stencil
        buffer to avoid triangulation. Their idea is to connect all points on the curve path and draw them as a triangle
        fan into the stencil buffer with the invert operator. Only pixels drawn an odd number of times will be nonzero,
        thus giving the correct image of concavities and holes. Next, they draw the curve segments, treating them all as
        convex quadratic elements. This will either add to or carve away a curved portion of the shape. A quad large
        enough to cover the extent of the stencil buffer is then drawn to the frame buffer with a stencil test. The
        result is the same as ours without triangulation or subdivision, and needing only one quadratic curve
        orientation. Furthermore, eliminating the triangulation steps makes high-performance rendering of dynamic curves
        possible. The disadvantage of their approach is that two passes over the curve data are needed. For static
        curves, they are trading performance for implementation overhead.</p>

      <h2>25.5 Antialiasing</h2>

      <p>We present an approach to antialiasing in the pixel shader based on a signed distance approximation to a curve
        boundary. By reducing pixel opacity within a narrow band that contains the boundary, we can approximate
        convolution with a filter kernel. However, this works only when pixel samples lie on both sides of a boundary,
        such as points well inside the Bézier convex hull of a curve. For points near triangle edges, or when the edge
        of a triangle is the boundary, this scheme breaks down. Fortunately, this is exactly the case that is handled by
        hardware <em>multisample antialiasing</em> (MSAA). MSAA uses a coverage mask derived as the percentage of
        samples (from a hardware-dependent sample pattern) covered by a triangle. Only one pixel shader call is
        initiated, and this is optionally located at the centroid of the covered samples, as opposed to the pixel
        center, to avoid sampling outside the triangle's image in texture space. In our case, out-of-gamut sampling is
        not a problem, because we use a procedural definition of a texture (an algebraic equation). Therefore, centroid
        sampling is not recommended.</p>

      <p>For antialiasing of curved boundaries on the interior of the Bézier convex hull, we need to know the
        screen-space signed distance from the current pixel to the boundary. If this distance is ±½ a pixel (an
        empirically determined choice; this could be less or more), then the opacity of the pixel color is changed
        relative to the pixel's distance to the curved boundary. Computing the true distance to a degree <em>d</em>
        polynomial curve requires the solution to a degree 2<em>d</em> - 1 equation. This is impractical on today's
        hardware, for performance reasons.</p>

      <p>Instead, we use an approximate signed distance based on gradients. For a function <em>f</em> (<em>x</em>,
        <em>y</em>), the gradient of <em>f</em> is a vector operator
        <img src="https://developer.download.nvidia.com/books/gpugems3/U2207.GIF" class="articleIcon" alt="U2207.GIF"><em>f</em>
        = [d<em>f</em>/<em>x</em> <em>f</em>/<em>y</em>]. The GPU has hardware support for taking gradients of variables
        in pixel shader programs via the <tt>ddx()</tt> and <tt>ddy()</tt> functions. We define the signed distance
        function to the screen-space curve <em>f</em> (<em>x</em>, <em>y</em>) = 0 to be</p>

      <p><img src="https://developer.download.nvidia.com/books/gpugems3/0557equ01.jpg" alt="0557equ01.jpg"></p>

      <p>In our case, the implicit function is not defined in screen (pixel) space. However, the process of
        interpolating procedural texture coordinates in screen space is, in effect, mapping screen [<em>x y</em>] space
        to procedural texture coordinate space ([<em>u v</em>] for quadratics, [<em>k l m</em>] for cubics). In other
        words, we can think of the interpolated procedural texture coordinates as vector functions</p>

        <tbody>
        <tr>
          <td>
            <p>[<em>u</em>(<em>x</em>, <em>y</em>)</p>
          </td>

          <td>

          </td>

          <td>

          </td>
        </tr>

      </table>

      <p>Each of these coordinate functions is actually the ratio of linear functionals whose quotient is taken in
        hardware (that is, perspective correction). An implicit function of these coordinate functions is a composition,
        defining a screen-space implicit function. Therefore, our signed distance function correctly measures
        approximate distance in pixel units.</p>

      <p>Hardware gradients are based on differences between values of adjacent pixels, so they can only approximate the
        derivatives of higher-order functions. Although this rarely (if ever) results in artifacts, with only a few
        additional math operations, we can get exact derivatives by applying the chain rule to our shader equations. Let
        the following,</p>

      <table>
        <tbody>

            <p><em>q</em>(<em>x</em>, <em>y</em>) = <em>u</em>(<em>x</em>, <em>y</em>)<sup>2</sup> -
              <em>v</em>(<em>x</em>, <em>y</em>) = 0 and</p>
          </td>
        </tr>

          </td>
        </tr>

      <p>We can write our signed distance function as</p>

        <img src="https://developer.download.nvidia.com/books/gpugems3/U2190.GIF" class="articleIcon" alt="U2190.GIF">
        <em>q</em> for quadratics and <em>f</em>

        <em>c</em> for cubics. For a boundary interval of ±½ pixel, we map signed distance to opacity by <em>a</em> = ½
        - <em>sd</em>. This is based on a linear ramp blending; higher-order blending could be used at higher cost. If
        <em></em> &gt; 1, we set <em></em>

      <h2>25.6 Code</h2>

      <p>Listing 25-1 is HLSL code for our quadratic shader. The code for the cubic shader is similar.</p>

      <h4>Example 25-1. Quadratic Curve Pixel Shader</h4>

      <pre><code class="language-cpp">
float4 QuadraticPS(float2 p : TEXCOORD0, float4 color : COLOR0) : COLOR
{
  // Gradients
  float2 px = ddx(p);
  float2 py = ddy(p);
  // Chain rule
  float fx = (2 * p.x) * px.x - px.y;
  float fy = (2 * p.x) * py.x - py.y;
  // Signed distance
  float sd = (p.x * p.x - p.y) / sqrt(fx * fx + fy * fy);
  // Linear alpha
  float alpha = 0.5 - sd;
  if (alpha &gt; 1)
    // Inside
    color.a = 1;
  else if (alpha &lt; 0)
    // Outside
    clip(-1);
  else
    // Near boundary
    color.a = alpha;
  return color;
}</code></pre>

      <h2>25.7 Conclusion</h2>

      <p>We have presented an algorithm for rendering vector art defined by closed paths containing quadratic and cubic
        Bézier curves. We locally triangulate each Bézier convex hull and globally triangulate the interior (right-hand
        side) of each path. We assign procedural texture coordinates to the vertices of each Bézier convex hull. These
        coordinates encode linear functionals and are interpolated by the hardware during rasterization. The process of
        interpolation maps the procedural texture coordinates to a space where the implicit equation of the curve has a
        simple form: <em>u</em> <sup>2</sup> - <em>v</em> = 0 for quadratics and <em>k</em> <sup>3</sup> - <em>lm</em> =
        0 for cubics. A pixel shader program evaluates the implicit equation. The sign of the result will determine if a
        pixel is inside (negative) or outside (positive). We use hardware gradients to approximate a screen-space signed
        distance to the curve boundary. This signed distance is used for antialiasing the curved boundaries. We can
        apply an arbitrary projective transform to view our plane curves in 3D. The result has a small and static memory
        footprint, and the resulting image is resolution independent.
        <a href="javascript:popUp('elementLinks/25fig07.jpg')">Figure 25-7</a> shows an example of some text rendered in
        perspective using our technique.</p>

      <div class="figure">
        <a href="javascript:popUp('elementLinks/25fig07.jpg')"><img src="https://developer.download.nvidia.com/books/gpugems3/25fig07.jpg" alt="25fig07.jpg"></a>
        <p><a href="javascript:popUp('elementLinks/25fig07.jpg')">Figure 25-7</a> Our Algorithm Is Used to Render 2D
          Text with Antialiasing Under a 3D Perspective Transform</p>
      </div>

      <p>In the future, we would like to extend this rendering paradigm to curves of degree 4 and higher. This would
        allow us to apply freeform deformations to low-order shapes (such as font glyphs) and have the resulting
        higher-order curve be resolution independent. The work of Kokojima et al. 2006 showed how to render dynamic
        quadratic curves; we would like to extend their approach to handle cubic curves as well. This is significantly
        more complicated than the quadratic case, because of the procedural texture-coordinate-assignment phase.
        However, it should be possible to do this entirely on the GPU using DirectX 10-class hardware equipped with a
        geometry shader (Blythe 2006).</p>
