id=name-origin><a href=#name-origin>Where did the name Roc come from?</a></h2><p>The Roc programming language is named after <a href=https://en.wikipedia.org/wiki/Roc_(mythology)>a mythical bird</a>.<p><svg aria-labelledby="logo-svg-title logo-svg-desc" width="240" height="240" viewBox="0 0 51 53" fill="none"><title id="logo-svg-title">The Roc logo</title><desc id="logo-svg-desc">A class="logo-dark"/></svg><p>That's why the logo is a bird. It’s specifically an <a href=https://youtu.be/9gni1t1k1uY><em>origami</em> bird</a> as an homage
to <a href=https://elm-lang.org/>Elm</a>’s tangram logo.<p>Roc is a direct descendant of Elm. The languages are similar, but not the same.
<a href=https://en.wikipedia.org/wiki/Origami>Origami</a> likewise has similarities to <a href=https://en.wikipedia.org/wiki/Tangram>tangrams</a>, although they are not the same.
Both involve making a surprising variety of things
from simple primitives. <a href=https://en.wikipedia.org/wiki/Fold_(higher-order_function)><em>Folds</em></a>
are also common in functional programming.<p>The logo was made by tracing triangles onto a photo of a physical origami bird.
It’s made of triangles because triangles are a foundational primitive in
computer graphics.<p>The name was chosen because it makes for a three-letter file extension, it means something
fantastical, and it has incredible potential for puns. Here are some different ways to spell it:<ul><li><strong>Roc</strong> - traditional<li><strong>roc</strong> - low-key<li><strong>ROC</strong> - <a href=https://package.elm-lang.org/packages/elm/core/latest/String#toUpper>YELLING</a><li><strong>Röc</strong> - <a href=https://en.wikipedia.org/wiki/Metal_umlaut>metal 🤘</a></ul><p>Fun fact: "roc" translates to 鹏 in Chinese, <a href="https://www.mdbg.net/chinese/dictionary?page=worddict&amp;wdrst=0&amp;wdqb=%E9%B9%8F">which means</a> "a large fabulous bird."<h2 id=strings-in-roc><a href=#strings-in-roc>Why does Roc not handle strings like most languages?</a></h2><p>We want to help you make reliable software, so we aim to make sure that you're aware of all the pitfalls when handling
strings. In many cases, the functions available in the built-in <a href=https://www.roc-lang.org/docs/main/Str><code>Str</code></a> type are
sufficient (it has <code>concat</code>, <code>contains</code>, <code>starts_with</code> and many more functions). You can also use <code>Str.to_utf8</code> to
convert a <code>Str</code> to a <code>List(U8)</code>, perform some operations, then convert back to <code>Str</code> using <code>Str.from_utf8</code>. However,
Unicode is a complex and evolving topic, so it is usually best handled by a dedicated library, such as
<a href=https://github.com/roc-lang/unicode>roc-lang/unicode</a>: check it out! For pure ASCII text, you may prefer to use a
dedicated library such as <a href=https://github.com/Hasnep/roc-ascii>Hasnep/roc-ascii</a>.<h2 id=import-everything><a href=#import-everything>Why can't <code>exposing</code> import everything?</a></h2><p>Roc can bring specific public definitions into scope with an import such as <code>import Http exposing [Request, Response]</code>.
You can also import the type itself using <code>import Http</code>, then use <code>Http.Request</code> and <code>Http.Response</code>.
There is intentionally no wildcard form that brings every public definition into scope. Some languages provide one
because it can be convenient, but it also has downsides.<p>A minor reason Roc doesn't have wildcard imports is that they can make it more difficult outside the editor (e.g. on a
website) to tell where something comes from, especially if multiple imports are using them. ("I don't see <code>blah</code> defined
in this file, so it must be coming from an import...but which of these several wildcard imports could it be? I'll have
to check all of them, or download this code base and open it up in the editor so I can jump to definition!")<p>The main reason for this design, though, is compiler performance.<p>Currently, the name resolution step in compilation can be parallelized across modules, because it's possible to
tell if there's a naming error within a module using only the contents of that module. If "expose everything" is
allowed, then it's no longer clear whether anything is a naming error or not, until all the "expose everything"
modules have been processed, so we know exactly which names they expose. Because that feature doesn't exist in Roc,
all modules can do name resolution in parallel.<p>Allowing wildcard imports would only impose that cost on files that used them. However, when people discover ways
to speed up builds, advice starts to circulate about avoiding slower features. If Roc had wildcard imports, a
predictable recommendation would eventually be: "don't use this feature because it slows down your builds."<p>If a feature exists in a language, but the common recommendation is never to use it, that's cause for reconsidering
whether the feature should be in the language at all. In the case of this feature, it's simpler if the
language doesn't have it; that way nobody has to learn (or spend time spreading the word) about the
performance-boosting advice not to use it.<h2 id=option-type><a href=#option-type>Why doesn't Roc have a <code>Maybe</code> or <code>Option</code> or <code>Optional</code> type, or <code>null</code> or <code>nil</code> or <code>undefined</code>?</a></h2><p>It's common for programming languages to have a <a href=https://en.wikipedia.org/wiki/Null_pointer>null reference</a>
(e.g. <code>null</code> in C, <code>nil</code> in Ruby, <code>None</code> in Python, or <code>undefined</code> in JavaScript).
The inventor of the null reference refers to it as his "<a href=https://en.wikipedia.org/wiki/Null_pointer#History>billion dollar mistake</a>" because it "has led to innumerable errors, vulnerabilities, and system crashes, which have probably caused a billion dollars of pain and damage in the last forty years."<p>For this and other reasons, many languages do not include a null reference, but instead have a standard library
data type which can be used in situations where a null reference would otherwise be used. Common names for this
null reference alternative type include <code>Maybe</code> (like in Haskell or Elm), <code>Option</code> (like in OCaml or Rust),
and <code>Optional</code> (like in Java).<p>By design, Roc does not have one of these. There are several reasons for this.<p>First, if a function returns a potential error, Roc has the convention to use <code>Try</code> with an error type that
has a single tag describing what went wrong. (For example, <code>List.first : List(item) -> Try(item, [ListWasEmpty, ..])</code>
instead of <code>List.first : List(item) -> Maybe(item)</code>.) This is not only more self-descriptive, it also composes better with
other operations that can fail; there's no need to have functions like <code>Try.to_maybe</code> or <code>Maybe.to_try</code>,
because in Roc, the convention is that operations that can fail always use <code>Try</code>.<p>To describe something that's not an operation that can fail, an explicit tag union can be
more descriptive than something like <code>Maybe</code>. For example, if a record type has an <code>artist</code> field, but the artist
information may not be available, compare these three alternative ways to represent that:<ul><li><code>artist : Maybe(Artist)</code><li><code>artist : [Loading, Loaded(Artist)]</code><li><code>artist : [Unspecified, Specified(Artist)]</code></ul><p>All three versions tell us that we might not have access to an <code>Artist</code>. However, the <code>Maybe</code> version doesn't
tell us why that might be. The <code>Loading</code>/<code>Loaded</code> version tells us we don't have one <em>yet</em>, because we're
still loading it, whereas the <code>Unspecified</code>/<code>Specified</code> version tells us we don't have one and shouldn't expect
to have one later if we wait, because it wasn't specified.<p>Naming aside, using explicit tag unions also makes it easier to transition to richer data models. For example,
after using <code>[Loading, Loaded(Artist)]</code> for awhile, we might realize that there's another possible state: loading
failed due to an error. If we modify this to be <code>[Loading, Loaded(Artist), Errored(LoadingErr)]</code>, all
of our code for the <code>Loading</code> and <code>Loaded</code> states will still work.<p>In contrast, if we'd had <code>Maybe(Artist)</code> and were using helper functions like <code>Maybe.is_none</code> (a common argument
for using <code>Maybe</code> even when it's less self-descriptive), we'd have to rewrite all the code which used those
helper functions. As such, a subtle downside of these helper functions is that they discourage any change to
the data model that would break their call sites, even if that change would improve the data model overall.<p>On a historical note, <code>Maybe</code> may have been thought of as a substitute for null references—as opposed to something that emerged organically based on specific motivating use cases after <code>Result</code> (=<code>Try</code>) already existed. That said, in languages that do not have an equivalent of Roc's tag unions, it's much less ergonomic to write something like <code>Try(a, [ListWasEmpty])</code>, so that design would not fit those languages as well as it fits Roc.<h2 id=arbitrary-numbers><a href=#arbitrary-numbers>Why doesn't Roc have a builtin "arbitrary-sized" number type like BigNum or BigDecimal?</a></h2><p>Like all programming languages, Roc is subject to the limitations of the universe. Almost all numbers in mathematics cannot even be represented in the universe because you'd run out of matter trying to write them down, and therefore Roc must choose what subset of mathematics to support—including which numbers to support.<p>Roc supports 128-bit integers and 128-bit fixed-point decimal numbers. Here are some approximate ranges for those:<ul><li><code>I128</code>: ±170000000000000000000000000000000000000<li><code>Dec</code>: ±170000000000000000000.000000000000000000</ul><p>For heap-allocated numbers to be worth including in Roc's builtins, a sufficient number of real-world use cases would need to exist where the above ranges are too small, but a heap-allocated number would be big enough, <em>and</em> the performance hit from the heap-allocated numbers would be acceptable to those use cases, <em>and</em> a user-created implementation of heap-allocated numbers would not be acceptable, <em>and</em> using 64-bit floating-point numbers (which can be even larger than these, at the cost of precision loss in some operations) would not be acceptable either.<p>So far, this has not happened.<h2 id=arbitrary-rank-types><a href=#arbitrary-rank-types>Why doesn't Roc have higher-kinded polymorphism or arbitrary-rank types?</a></h2><p><em>Since this is a FAQ answer, it assumes familiarity with higher-kinded types and higher-rank types instead of including a primer on them.</em><p>A valuable aspect of Roc's type system is that it has decidable <a href=https://en.wikipedia.org/wiki/Principal_type>principal</a>
type inference. This means that:<ul><li>At compile time, Roc can correctly infer the types for every expression in a program, even if you don't annotate any of the types.<li>This inference always infers the most general type possible; you couldn't possibly add a valid type annotation that would make the type more flexible than the one that Roc would infer if you deleted the annotation.</ul><p>It's been proven that any type system which supports either <a href=https://www.cl.cam.ac.uk/~jdy22/papers/lightweight-higher-kinded-polymorphism.pdf>higher-kinded polymorphism</a> or <a href=https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/putting.pdf>arbitrary-rank types</a> cannot have decidable
principal type inference. With either of those features in the language, there will be situations where the compiler
would be unable to infer a type—and you'd have to write a type annotation. This also means there would be
situations where the editor would not be able to reliably tell you the type of part of your program, unlike today
where it can accurately tell you the type of anything, even if you have no type annotations in your entire code base.<p>This is one factor that higher-rank and higher-kinded types have in common. There are other factors which are specific
to each.<h3 id=higher-rank-types><a href=#higher-rank-types>Higher-rank types</a></h3><p>Supporting higher-rank types in Roc has been discussed before, but it has several important downsides:<ul><li>It would increase the complexity of the language.<li>It would make some compiler error messages more confusing (e.g. they might mention <code>forall</code> because that was the most general type that could be inferred, even if that wasn't helpful or related to the actual problem).<li>It would substantially increase the complexity of the type checker, which would necessarily slow it down.<li>It would make some Roc programs run significantly more slowly. Roc compiles programs by <a href=https://en.wikipedia.org/wiki/Monomorphization>monomorphizing</a>, and it's unclear how we could fully monomorphize programs containing Rank-2 types. This means compiling programs which include Rank-2 types (or higher) would require sacrificing monomorphization, which would substantially degrade runtime performance.</ul><p>As such, the plan is for Roc to stick with Rank-1 types indefinitely.<h3 id=higher-kinded-polymorphism><a href=#higher-kinded-polymorphism>Higher-kinded polymorphism</a></h3><p>The explicit plan is that Roc will never support higher-kinded polymorphism.<p>On the technical side, the reasons for this are ordinary: like any language feature, HKP has both benefits and drawbacks,
and in the context of Roc, the drawbacks seem to outweigh the benefits. (Those who come to a different conclusion may
think HKP's drawbacks would be less of a big a deal in Roc. That's reasonable; we programmers often weigh the same
trade-offs differently.) To be clear, this analysis of HKP is in the specific context of Roc; there are plenty of
other languages where HKP seems like a great fit. For example, it's hard to imagine Haskell without it. Similarly,
lifetime annotations might be a natural fit for Rust, but they wouldn't be a good fit for Roc either.<p>It's also important to consider the cultural implications of deciding whether or not to support HKP.
To illustrate these implications, imagine this conversation:<p><strong>Programmer 1:</strong> "How do you feel about higher-kinded polymorphism?"<p><strong>Programmer 2:</strong> "I have no idea what that is."<p><strong>Programmer 1:</strong> "Okay, how do you feel about monads?"<p><strong>Programmer 2:</strong> "OH NO."<p>For some, this conversation does not require imagining, because it's so familiar: higher-kinded types come up in
conversation, another programmer asks what that means, monads are given as an example, and their reaction is
strongly negative. On the flip side, plenty of programmers love HKP and vigorously advocate for its addition
to languages they use which don't have it. Feelings about HKP seem strongly divided, maybe more so
than any other type system feature besides static and dynamic types.<p>It's impossible for a programming language to be neutral on this. If the language doesn't support HKP, nobody can
implement a Monad typeclass (or equivalent) in any way that can be expected to catch on. Advocacy to add HKP to the
language will inevitably follow. If the language does support HKP, one or more alternate standard libraries built
around monads will inevitably follow, along with corresponding cultural changes. (See Scala for example.)
Culturally, to support HKP is to take a side, and to decline to support it is also to take a side.<p>Given this, languages have three options:<ul><li>Have HKP and have Monad in the standard library. Embrace them and build a culture and ecosystem around them.<li>Have HKP and don't have Monad in the standard library. An alternate standard library built around monads will inevitably emerge, and both the community and ecosystem will divide themselves along pro-monad and anti-monad lines.<li>Don't have HKP; build a culture and ecosystem around other things.</ul><p>Considering that these are the only three options, an early decision in Roc's design—not only on a technical
level, but on a cultural level as well—was to make it clear that the plan is for Roc never to support HKP.
The hope is that this clarity can save a lot of community members' time that would otherwise be spent on advocacy or
arguing between the two sides of the divide. Again, it's completely reasonable for anyone to have a different preference,
but given that languages can only choose one of these options, it seems clear that the right choice for Roc
is for it to never have higher-kinded polymorphism.<h2 id=curried-functions><a href=#curried-functions>Why aren't Roc functions curried by default?</a></h2><p>Although technically any language with first-class functions makes it possible to curry
any function (e.g. anyone can manually curry a Roc function <code>|x, y, z|</code> by writing <code>|x| |y| |z|</code> instead),
typically what people mean when they say Roc isn't a curried language is that Roc functions aren't curried
by default. The rest of this section will use "currying" as a shorthand for "functions that are curried
by default" for the sake of brevity.<p>Currying makes function calls more concise in some cases, but it has several significant downsides:<ul><li>It lowers error message quality, because there can no longer be an error for "function called with too few arguments." (Calling a function with fewer arguments is always valid in curried functions; the error you get instead will unavoidably be some other sort of type mismatch, and it will be up to you to figure out that the real problem was that you forgot an argument.)<li>It significantly increases the language's learning curve. (More on this later.)<li>It facilitates pointfree function composition. (More on why this is listed as a downside later.)</ul><p>There's also a downside that it would make runtime performance of compiled programs worse by default,
but it would most likely be possible to optimize that away at the cost of slightly longer compile times.<p>These downsides seem to outweigh the one upside (conciseness in some places). Here are some more details about
the downsides.<h3 id=curried-learning-curve><a href=#curried-learning-curve>Currying and learning curve</a></h3><p>Currying leads to function signatures that look surprising to beginners. For example, in Roc, the
<code>Bool.is_eq</code> function has the type <code>Bool, Bool -> Bool</code>. If Roc were a
curried language, this function would instead have the type <code>Bool -> Bool -> Bool</code>. Since no mainstream programming
languages today are curried, anyone who knows a mainstream language and is learning their first curried language will
require additional explanation about why function types look this way.<p>This explanation is nontrivial. It requires explaining partial application, how curried functions facilitate partial
application, how function signatures accurately reflect that they're curried, and going through examples for all of these.
All of it builds up to the punchline that "technically, all functions in this language have a single argument," which
some percentage of learners find interesting, and some percentage still find confusing even after all that explanation.<p>It's common for beginners to report that currying only "clicked" for them after spending significant time writing code
in a curried language. This is not the end of the world, especially because it's easy enough to think "I still don't
totally get this even after that explanation, but I can remember that function arguments are separated by <code>-></code> in this
language and maybe I'll understand the rest later." Clearly currying doesn't preclude a language from being easy to learn,
because Elm has currying, and Elm's learning curve is famously gentle.<p>That said, beginners who feel confused while learning the language are less likely to continue with it.
And however easy Roc would be to learn if it had currying, the language is certainly easier to learn without it.<h3 id=pointfree-composition><a href=#pointfree-composition>Pointfree function composition</a></h3><p><a href=https://en.wikipedia.org/wiki/Tacit_programming>Pointfree function composition</a> is where you define
a new function by composing together two existing functions without naming intermediate arguments.
Here's an example:<pre><samp>normalize <span class=colon>:</span> Str <span class=op>-&gt;</span> Str
normalize <span class=op>=</span> compose<span class=paren>(</span>Str<span class=op>.</span>trim<span class=comma>,</span> Str<span class=op>.</span>with_ascii_lowercased<span class=paren>)</span>

compose <span class=colon>:</span> <span class=paren>(</span>a <span class=op>-&gt;</span> b<span class=paren>)</span><span class=comma>,</span> <span class=paren>(</span>c <span class=op>-&gt;</span> a<span class=paren>)</span> <span class=op>-&gt;</span> <span class=paren>(</span>c <span class=op>-&gt;</span> b<span class=paren>)</span>
compose <span class=op>=</span> <span class=op>|</span>f<span class=comma>,</span> g<span class=op>|</span> <span class=op>|</span>x<span class=op>|</span> f<span class=paren>(</span>g<span class=paren>(</span>x<span class=paren>)</span><span class=paren>)</span>
</samp></pre><p>Here's a way to write it without pointfree function composition:<pre><samp>normalize <span class=colon>:</span> Str <span class=op>-&gt;</span> Str
normalize <span class=op>=</span> <span class=op>|</span>str<span class=op>|</span> str<span class=op>.</span>with_ascii_lowercased<span class=paren>(</span><span class=paren>)</span><span class=op>.</span>trim<span class=paren>(</span><span class=paren>)</span>
</samp></pre><p>It's common for programmers to build a mental model of what <code>compose(Str.trim, Str.with_ascii_lowercased)</code> does by mentally
translating it into <code>|str| str.with_ascii_lowercased().trim()</code>. This extra mental translation step makes it take
longer to read and to understand despite being technically more concise. In more complex examples (this
is among the tamest of pointfree function composition examples), the chances increase of making a mistake in
the mental translation step, leading to a misunderstanding of what the function is doing—which can cause bugs.<p>Some languages place such a high value on conciseness that they would consider the conciseness upside to outweigh
these downsides, but Roc is not one of those languages. It's considered stylistically better in Roc to write the
second version above. Given this, since currying facilitates pointfree function composition, making Roc a curried
language would have the downside of facilitating an antipattern in the language.<p>Stacking up all these downsides of currying against the one upside of making certain function calls more concise,
it seems clear that Roc should not be a curried language.<h2 id=advanced-types><a href=#advanced-types>Will Roc ever have linear types, dependent types, refinement types, or uniqueness types?</a></h2><p>The plan is for Roc to never have linear types, dependent types, refinement types, or uniqueness types.<p>Fast compile times are a primary goal for Roc, and a major downside of refinement types is an exponential increase in compile times. This rules out refinement types for Roc.<p>If Roc were to have linear types or uniqueness types, they would move things that are currently behind-the-scenes performance optimizations into the type system. For them to be effective across the ecosystem, they couldn't really be opt-in; everyone would have to use them, even those for whom the current system of behind-the-scenes optimizations already met their performance needs without any added type system complexity. Since the overwhelming majority of use cases are expected to fall into that latter group, adding linear types or uniqueness types to Roc would be a net negative for the ecosystem.<p>Dependent types are too risky of a bet for Roc to take. They have been implemented in programming languages for three decades, and for at least half that time period, it has been easy to find predictions that dependent types will be the future of type systems. Much harder to find are success stories of complex applications built with dependent types, which realized benefits that significantly outweighed the substantial complexity of introducing value semantics to a type system.<p>Perhaps more success stories will emerge over time, but in the meantime it remains an open question whether dependent types are net beneficial in practice to application development. Further experimentation would be required to answer this question, and Roc is not the right language to do those experiments.<h2 id=multiple-platforms><a href=#multiple-platforms>Can one application have multiple platforms? Can platforms compose?</a></h2><p>The short answer to each of these questions is "No." To understand why, it's helpful to look at this from the platform author's perspective.<p>Building a Roc platform means implementing two things:<ol><li>The public-facing Roc API. This is the part the application author sees.<li>The "host," which provides the lower-level implementation behind that API. The host isn't written in Roc, and isn't visible to the application author.</ol><p>Let's say I'm writing a platform and I decide to implement the host in C.<p>My C code will compile to an executable which does something like this:<ol><li>Start running the program<li>At some point, call a function named something like "roc_app_main"<li>That roc_app_main function will result in the actual Roc application code running.</ol><p>An important characteristic of this design is that the platform is in complete control of when all the Roc code runs. If the host is written in C, that C code will specify the <code>main()</code> function that runs when the compiled binary runs. (The Roc application might also have something named <code>main</code>, but that just compiles down to a pure function the C host can choose to call—or not—whenever it pleases.)<p>One of the main goals of this design is to give platform authors the ability to make a coherent experience for a specific domain. The public API can omit operations that aren't implementable in a particular host, or which wouldn't make sense in the target domain. The host has enough information to use any kind of asynchronous I/O system they like, or synchronous blocking I/O if that makes more sense.<p>The single-platform design is based around the idea of giving a platform author exclusive control over which primitives are available and how they're implemented at a low level. Exclusivity is the point! It's not really clear how "multiple platforms" or "composed platforms" would work, but certainly it would require sacrificing the current benefit of one platform being able to provide a cohesive experience for its domain.<p>With all that in mind, it's possible to write Roc code that can be used across multiple platforms. Applications can use platform-agnostic packages, as well as packages involving I/O, as long as their platform supports the I/O operations in question.<p>Similarly, platforms can share code for common Roc logic using normal Roc packages. Code can also be shared between hosts using whatever normal code sharing mechanisms their chosen host languages support.<p>Putting all this together, applications have exactly one platform, which enables platform authors to create a cohesive experience optimized for a particular domain, and both application authors and platform authors can share code as much as they like.<h2 id=other-compilation-targets><a href=#other-compilation-targets>Will Roc ever compile to JavaScript, JVM/CLR/BEAM bytecode, or other higher-level targets?</a></h2><p>The plan is for Roc to compile only to very low-level targets like machine code and WebAssembly.<p>This is partly in order to keep the scope of the project smaller, but also because supporting higher-level targets could make it significantly more difficult to create an ecosystem of high-performance Roc packages. Techniques which are performance optimizations on low-level targets like machine code or WebAssembly might actually impede performance on higher-level targets, and vice versa.<p>Additionally, some of these higher-level targets may not be able to represent Roc's full range of numbers efficiently (e.g. Roc's very common <code>U64</code> would be represented in JavaScript as <a href=https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/BigInt>a heap-allocated <code>BigInt</code></a>, which would be massively slower), and their string representations may not work well with Roc's builtins (e.g. Roc's <code>Str</code> uses UTF-8 and has operations which let you traverse those bytes directly, although the JVM, CLR, and JavaScript all use UTF-16).<p>Fortunately, since these higher-level targets tend to support some combination of C FFI, WebAssembly calls, or both, there's already a path to use Roc code in those environments even if Roc doesn't directly compile to their higher-level bytecode.<h2 id=self-hosted-compiler><a href=#self-hosted-compiler>Will Roc's compiler ever be self-hosted? (That is, will it ever be written in Roc?)</a></h2><p>The plan is to never implement Roc's compiler in Roc.<p>The goal is for Roc's compiler to deliver the best user experience possible. Compiler performance is strongly influenced by how memory is used, and there are many performance benefits to be gained from using a systems language like Zig which offers more direct control over memory than Roc ever should.<p>Roc isn't trying to be the best possible language for high-performance compiler development, but it is trying to have a high-performance compiler. The best tool for that job is a language other than Roc, so that's what we're using!<h2 id=permissive-license><a href=#permissive-license>Why does Roc use the license it does?</a></h2><p>The short explanation for why Roc is released under the <a href=https://opensource.org/licenses/UPL>Universal Permissive License</a>:<ul><li>Like <a href=https://opensource.org/licenses/MIT>MIT</a>, it's permissive and concise<li>Like <a href=https://opensource.org/licenses/Apache-2.0>Apache2</a>, it protects against contributors claiming software patents over contributed code after the fact (MIT and BSD do not include protections against this)<li>It's compatible with <a href=https://opensource.org/licenses/GPL-2.0>GPLv2</a> (which <a href=https://www.apache.org/licenses/GPL-compatibility.html>Apache2 is not</a>)<li>It's one license, unlike "MIT or Apache2, at your choice" (which is how <a href=https://internals.rust-lang.org/t/rationale-of-apache-dual-licensing/8952/4>Rust addressed the problem</a> of MIT not having patent protections but Apache2 not being GPLv2 compatible)<li>It's been approved by OSI, FSF, and Oracle's lawyers, so it has been not only vetted by three giants in the world of software licensing, but also three giants with competing interests - and they all approved it.</ul><p>There's also <a href=https://github.com/roc-lang/roc/issues/1199>a longer explanation</a> with more detail about the motivation and thought process, if you're interested.<h2 id=function-equality><a href=#function-equality>Why can't functions be compared for equality using the <code>==</code> operator?</a></h2><p>Function equality has been proven to be undecidable in the general case because of the <a href=https://en.wikipedia.org/wiki/Halting_problem>halting problem</a>.
So while we as humans might be able to look at <code>|x| x + 1</code> and <code>|x | 1 + x</code> and know that they're equivalent,
in the general case it's not possible for a computer to do this reliably.<p>There are some other potential ways to define function equality, but they all have problems.<p>One way would be to have two functions be considered equal if their source code is equivalent. (Perhaps disregarding
comments and spaces.) This sounds reasonable, but it means that now revising a function to do
exactly the same thing as before (say, changing <code>|x| x + 1</code> to <code>|x| 1 + x</code>) can cause a bug in a
distant part of the code base. Defining function equality this way means that revising a function's internals
is no longer a safe, local operation - even if it gives all the same outputs for all the same inputs.<p>Another option would be to define it using "reference equality." This is what JavaScript does, for example.
However, Roc does not use reference equality anywhere else in the language, and it would mean that (for example)
passing <code>|x| x + 1</code> to a function compared to defining <code>fn = |x| x + 1</code> elsewhere and then passing <code>fn</code> into
the function might give different answers.<p>Both of these would make revising code riskier across the entire language, which is very undesirable.<p>Another option would be to define that function equality always returns <code>False</code>. So both of these would evaluate
to <code>False</code>:<pre><samp><span class=paren>(</span><span class=op>|</span>x<span class=op>|</span> x <span class=op>+</span> <span class=number>1</span><span class=paren>)</span> <span class=op>==</span> <span class=paren>(</span><span class=op>|</span>x<span class=op>|</span> <span class=number>1</span> <span class=op>+</span> x<span class=paren>)</span> <span class=comment># False</span>
<span class=paren>(</span><span class=op>|</span>x<span class=op>|</span> x <span class=op>+</span> <span class=number>1</span><span class=paren>)</span> <span class=op>==</span> <span class=paren>(</span><span class=op>|</span>x<span class=op>|</span> x <span class=op>+</span> <span class=number>1</span><span class=paren>)</span> <span class=comment># False</span>
</samp></pre><p>This makes function equality effectively useless, while still technically allowing it. It has some other downsides:<ul><li>Now if you put a function inside a record, using <code>==</code> on that record will still type-check, but it will then return <code>False</code>. This could lead to bugs if you didn't realize you had accidentally put a function in there - for example, because you were actually storing a different type (e.g. an opaque type) and didn't realize it had a function inside it.<li>If you put a function (or a value containing a function) into a <code>Dict</code> or <code>Set</code>, you'll never be able to get it out again. This is a common problem with <a href=https://en.wikipedia.org/wiki/NaN>NaN</a>, which is also defined not to be equal to itself.</ul><p>The first of these problems could be addressed by having function equality always return True instead of False (since that way it would not affect other fields' equality checks in a record), but that design has its own problems:<ul><li>Although function equality is still useless, <code>(|x| x + 1) == (|x| x)</code> returns <code>Bool.True</code>. Even if it didn't lead to bugs in practice, this would certainly be surprising and confusing to beginners.<li>Now if you put several different functions into a <code>Dict</code> or <code>Set</code>, only one of them will be kept; the others will be discarded or overwritten. This could cause bugs if a value stored a function internally, and then other functions relied on that internal function for correctness.</ul><p>Each of these designs makes Roc a language that's some combination of more error-prone, more confusing, and more
brittle to change. Disallowing function equality at compile time eliminates all of these drawbacks.<p>Note that you can provide a custom implementation of <code>is_eq</code> for an opaque type that contains a function,
in any way you like (including ignoring the function for equality).</main><footer><div id=footer><div id=gh-link><a id=gh-centered-link href=https://github.com/roc-lang/roc><svg viewBox="0 0 98 96" height="25" fill-rule="evenodd" clip-rule="evenodd" role="img" id="gh-logo"><path d="M48.854.0C21.839.0.0 22 0 49.217c0 21.756 13.993 40.172 33.405 46.69 2.427.49 3.316-1.059 3.316-2.362.0-1.141-.08-5.052-.08-9.127-13.59 2.934-16.42-5.867-16.42-5.867-2.184-5.704-5.42-7.17-5.42-7.17-4.448-3.015.324-3.015.324-3.015 4.934.326 7.523 5.052 7.523 5.052 4.367 7.496 11.404 5.378 14.235 4.074.404-3.178 1.699-5.378 3.074-6.6-10.839-1.141-22.243-5.378-22.243-24.283.0-5.378 1.94-9.778 5.014-13.2-.485-1.222-2.184-6.275.486-13.038.0.0 4.125-1.304 13.426 5.052a46.97 46.97.0 0112.214-1.63c4.125.0 8.33.571 12.213 1.63 9.302-6.356 13.427-5.052 13.427-5.052 2.67 6.763.97 11.816.485 13.038 3.155 3.422 5.015 7.822 5.015 13.2.0 18.905-11.404 23.06-22.324 24.283 1.78 1.548 3.316 4.481 3.316 9.126.0 6.6-.08 11.897-.08 13.526.0 1.304.89 2.853 3.316 2.364 19.412-6.52 33.405-24.935 33.405-46.691C97.707 22 75.788.0 48.854.0z"/></svg><span id=gh-link-text>roc-lang/roc</span></a></div></div></footer>
