**Proposed edit.** Add the rule to edge 2's text as a named residual with its

than only from a roadmap backflow note eighteen hundred lines into another file.

## 4. `docs/bootstrap-sequence.md` — PREDATES (high)

**Current state.** 55 lines, status draft, **updated 2026-06-16**. It predates: the
two-rung ladder (`SELF-HOST-PLAN`, 2026-07-22), `decision-deployment-custody`
(2026-07-26), `decision-syscall-governance` (2026-07-28), `RUNG-2-MAP` (2026-07-28),
and `trust-boundary`'s 2026-08-05 update. Its frontmatter `related:` omits every one
of them.

**Why it is load-bearing.** `.planning/RUNG-2-MAP.md` line 42 lists the boot-path
requirement — CPU bring-up, master secret established in registers at boot, measured
boot for the pre-IOMMU window — with home `docs/bootstrap-sequence.md` and
**"no catalog element"**, build-state docs-only. This 55-line June draft *is* the
entire artifact behind one of Cluster 1's eight uncataloged rows.

**The substantive conflict.** The note describes **a** master secret: one passphrase
turned into a key schedule computed in-register, never written to RAM (TRESOR-style).
The intended install model is **N unlock positions with heterogeneous methods** —
none, password, keyfile, hardware key — individually tunable per position. These are
not the same design, and the difference is not cosmetic:

- Do all positions derive the *same* master secret by different paths, or does each
  hold distinct key material?
- If they reach the same protected range, the composite's strength is a **join**:
  a position unlocking with nothing next to one gated on a hardware token means the
  token bought nothing. That is a whole-assembly property, which
  `decision-profiles`' D4 already classifies — so it wants a **conformance row**,
  not a deployment guideline.

Settling this on paper is cheap now and ruinous to discover after a manifest format
exists.

**Also missing: the install ceremony.** `bootstrap-sequence` starts at power-on of
an already-installed system. `decision-deployment-custody` covers acquiring and
staging a moduleset. Neither covers the one-time event where unlock positions are
created and key material is first established — the seam between them.

**Proposed edit.** Bring the note current (rung split, related-list, a pointer to
`decision-deployment-custody`'s key-level ladder), state the plural-position
question as an explicit open item rather than silently assuming the singular, and
add an install-ceremony section or a sibling note. It should also carry the rung
honesty inline: hardware key levels are rung 2 by `decision-deployment-custody`, so
a rung-1 install is passphrase-derived keys in RAM under a Linux you don't control —
discipline, not enforcement. Design now, build where it stops being theater.

## 7. `TUI/docs/TERMINAL-PORT-DESIGN.md` — NEW (med)

**Two additions, both small.**

**§8, new item — freshness.** §3 gives "only the authority may write the trusted
region" and §3.4 honestly flags that this does not tell the human *which* region is
trusted. There is a sibling gap on the reflection side: typing gets you *this view
is faithful to a graph*, never *to the current graph*. Freshness is not a type
property, so a correct-but-stale render stays expressible, and an attack whose goal
*is* staleness — show the operator the authority set from before the grant — is
untouched by §3. Two candidate answers, neither free: put staleness-critical content
in the compositor-reserved region, or thread a linear observation token each render
consumes so a view cannot be re-derived from a stale observation. NEEDS-AUTHOR,
sibling to item 1.

**§1, acquisition paragraph.** It refers to "when profile-hands-caps lands" without
the element number. That is **E80**, audited and not implemented. Cite it — every
containment claim in §3 is conditioned on it, since the interim crossing that hands
`main` a `Terminal` today is ambient acquisition, which §3.2 otherwise forbids.

**§8 item 3 (cap granularity)** also now has an argument on one side: the
Clock/Timer precedent plus the agent case both point at split-early and
compositor-retains-and-grants. Still the author's call; worth recording that the
question has acquired a second constituency.

## 9. `.planning/SELF-IMPLEMENT-CATALOG.md` — NEW (med)

**No element for the install ceremony.** The nearest is **E43** (component broker:
AUTH/AUDIT, grant/revoke/audit), whose state column reads *spawn/teardown/
link-at-load only; edge 8*. Admitting a holder — staging a profile into a child
runtime that self-verifies, handing it an attenuated grant, retaining the one linear
port that is also the revocation handle — is E43's territory, but the install-time
half (creating unlock positions, first establishment of key material) is not
described anywhere in the catalog.

Two shapes, author's call: extend E43's row, or mint a separate element for the
ceremony and leave E43 as the runtime half. The second reads better, because the
ceremony happens once and the broker runs forever.

**Delegation's carrier is unpicked, and it's one decision for three rows.** Linearity
means handing a cap away loses it, so "parent keeps its authority, child gets a
weaker one" needs attenuate-then-split with the join of the shares no greater than
the original. Two carriers already exist: the subtype mechanism (implemented,
unwired to grant narrowing) and the coeffect semiring (**E38** — sums-to-no-more-than
is precisely what a semiring gives). **E78** is the same motion at the syscall floor.
Picking one carrier for all three would collapse a chunk of the capability rung into
a single build; picking three would triple it. Worth a docket item before any of the
three is specced.

**Catalog letter for the AI resident.** It is not `E#` (not the language) and
arguably not `T#` (not the terminal). Either a third series or an explicit decision
that it rides `T20+`.

## 10. `docs/decision-deployment-custody.md` — NEW, amendment only (low)

**The note is sound and settled** — the per-instance inversion table, personal-host
as a self-similar staged instance, and the key-level ladder (software levels
passphrase-derived/split-K-of-N → rung 1; physical and hardware levels TPM/token/
register custody → rung 2, out of scope until metal by design).

**What it now needs.** The ladder line assumes key levels are a *tier*, one per
instance. The intended model is **per-position tunability**, which makes the
composite a join across positions rather than a level. That is an amendment in the
house style — the way `decision-effect-facets` amends `decision-graded-kernel` —
not a rewrite. One paragraph: positions are plural, each carries its own method, and
the reachability of key material across positions is a whole-assembly conformance
question (D4), not a per-position one.

## Sequencing the fixes

Two are worth doing before anything else, for different reasons.

**Item 1 (ROADMAP)** because every other ordering claim in the project is read
against it, and it currently asserts the negation of the project's largest result.

**Item 3 (edge 2's erased-position rule)** because it is the only item on this list

the erased-witness pattern is conditioned on it, and it is cheap to settle.

Items 2, 4, 5 are mechanical-to-medium and independent of each other. Items 7–10 are
best done as one pass, since they are the same session's output landing in four
homes. Item 12 last, by construction.

**One caveat on this whole list.** It was assembled from a read-only snapshot with
`.git` excluded, so "the note says X, the tree says Y" is verifiable but "nobody has
fixed this yet" is not — an uncommitted edit or a commit after the snapshot would not
show. Check each against the working tree before acting.
