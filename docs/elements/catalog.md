Step 1 of the plan-and-audit arc (2026-07-06); extended 2026-07-21 with **E51–E68**
from the conformance map (`records/conformance-map.md`), which found ~13
actionable elements — the whole trust/custody/security novel core plus the self-host
linkage — that had no E-number and so could not be targeted by a worked-example.
Extended again 2026-07-21 with **E69–E71** (section IX) from the effect-algebra /
self-host-reach session (`docs/decisions/decision-effect-facets.md`,
`.planning/DELEGATION-MAP-2026-07-21.md`): the lowering reach self-hosting hides.
Every element chirality needs its own implementation of, grounded in the current tree. Three kinds are folded together
because all three are "things we must build ourselves":

- **SELF-HOST** — a judgment or a pipeline stage the compiler must own in chirality source.
- **REPLACE-CRUTCH** — a floor facility that must exist in chirality because nothing beneath
  it supplies one any more.
- **BUILD-PROPER** — a designed feature not yet built (or built only in miniature).

> **⚑ The first two kinds were re-founded 2026-08-31. The wording they replace is kept
> here, because this repo records its corrections.** Until this revision they read:
>
> - *SELF-HOST — Python we wrote that must become chirality source.*
> - *REPLACE-CRUTCH — a CPython/ctypes/libc convenience to shed as chirality self-hosts.*
>
> Both were defined against a baseline that no longer exists. The Python compiler oracle
> (`scaffold/chirality/*.py`) went with external judgment, and the CPython/ctypes host went
> with it; the 2026-08-31 migration then deleted `scaffold/` entirely. So the question those
> two definitions sorted on ("was there Python here?") is history, and it is no longer an
> axis this catalog can be read down: 63 rows named a Python file as their location, all 63
> of those files are gone, and both kinds now mean the same instruction, *build it in
> chirality*. What still separates them is only which side of the retired host boundary the
> behaviour used to sit on. The axes that carry state now are the **Track** column and the
> State cell.
>
> Four Python files survive on purpose and are outside this: `docs/examples/refs/gen-clock.py`,
> `gen-elf.py`, `gen-fdpass.py` and `gen-poll.py`, the ABI-fact generators. `HANDOFF.md` records
> that `pack` slices these four into pipeline bundles as the OURS baselines, so deleting them
> would cost four worked examples (E30, E31, E32, E34) their comparison. Nine tool scripts under
> `tools/` also remain, and `.planning/ZERO-PYTHON-SCOPE.md` sizes their replacement. "The Python
> is gone" is therefore true of the compiler oracle and false as a blanket statement.

The **Track** column (added 2026-08-31) says which of the author's two tracks a row is on,
per `HANDOFF.md` §"⚑ SCOPE, set by the author 2026-08-31: self-hosting only":

- **SH** — the current track: the language compiling and checking itself, and being good
  enough to write its own tooling, with zero Python. Every row the deferred track does not
  claim. SH is a track marker and carries no claim that a row is required for self-hosting,
  scheduled, or started.
- **OT** — the deferred ownership-and-trust track. Do not pull it into current work, and do
  not audit its documents.
- **?** — UNSORTED. Both tracks have a claim and only the author can settle it. Listed under
  §UNSORTED at the end of this file.

Sourcing, so a marker can be checked rather than believed. A row is **OT** if any of these
holds: **(a)** `HANDOFF.md`'s SCOPE sentence names it (the re-bootstrap climb, DDC, the secure
datum model, the register root, the cascade); **(b)** it sits in §VII (*the trust & custody
layer*) or §X (*the ownership requirement*), the two sections whose own headers declare them
the trust and ownership layer; **(c)** `LEDGER.md` files it under category **TR** (*Trust,
custody & security*). A row is **?** if **(d)** an audit has already put its track to the
author as an open question (E52, E71 — `.planning/handoffs/TEST-AUDIT-AND-SCOPE-RECATALOG.md`),
or **(e)** it sits in an SH category while its own text states its purpose to be an OT
element's payload (E78 on E40, E166/E167 on E53), or **(f)** the SCOPE sentence and a standing
decision read it opposite ways (E77). Everything else is **SH**.

Each row carries the **external reference** it corresponds to — the input to Step 2
(*what is OK to read/use for inspiration directly*). Step 2 has NOT been decided
here; the reference column only names the body-of-knowledge to review. Elements are
globally numbered (E#) for reference in later steps.

The **reference class** (a Step-2 hint, not a decision) is one of:
`OURS` (our own prior artifact, whatever its language — the port source; for most rows that
artifact was the Python oracle and is now evicted, which is why so many `OURS` cells name a
baseline that no longer exists and say so), `SPEC` (an interface contract we must
conform to — always readable), `PAPER` (an algorithm/idea in the literature),
`IMPL` (an existing open-source implementation — the real clean-room tension).

## VII. The trust & custody layer — BUILD-PROPER (category C, the novel core)

The identity-bearing novel layer (conformance map slices D/G; Fable audit F1/F2),
designed across `docs/decision-split-checker`, `certificate-discipline`, `split-role`,
`modules-custody`, `modules-security`, `modules-bridges` — almost no code today. Each
row is a distinct forcing-function whose worked-example forces the novel design through

## The Step-2 shape (preview, not decided here)

The reference column partitions cleanly for the "what's OK to read" call:

- **`OURS`** — our own Python (E1–E2, E13–E17, E23, E25, E49). Trivially fine to
  read; it *is* the port source.
- **`SPEC`** — interface contracts we must conform to bit-for-bit (E19–E21, E24,
  E28–E37, E34). Specs aren't a clean-room concern; you always read the ABI.
- **`PAPER`** — algorithms/ideas (E3–E12, E22, E26–E27, E38–E48, E50). Read the
  idea; the code is ours. This is where "inspiration vs. dependency" is mostly moot.
- **`IMPL`** — existing open-source implementations (Agda, Idris2, Z3, musl,
  dlmalloc). **This is the real Step-2 tension**: which of these may we read
  directly, and which must stay clean-room to keep the TCB/provenance story clean.

So Step 2's actual work is small and sharp: adjudicate the `IMPL` column
(and any `PAPER` whose only concrete realization is a specific codebase).
