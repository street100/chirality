# chirality native vs C: micro-benchmark results, 2026-08-01

Three kernels, each implemented with the same algorithm in chirality and in C,
timed as emitted x86-64 machine code (chirality) against gcc -O0 and -O2 (C).
No expected outcome was assumed; the numbers below are what was measured.

Rerun everything with one command:

    cd scaffold/bench && sh run.sh

The driver builds and runs under /tmp/chirality-bench (guest-local disk), writes
raw CSV plus disassembly evidence there, and prints the summary table.

## Headline numbers (median ns per iteration)

| kernel  | chirality native | gcc -O0 | gcc -O2 | native / -O0 | native / -O2 |
|---|---|---|---|---|---|
| arith   | 16.72 | 11.69 | 3.80 | 1.43x | 4.4x  |
| bytesum | 14.45 |  9.83 | 0.26 | 1.47x | 56.6x |
| states  | 17.51 | 14.72 | 0.73 | 1.19x | 24.0x |

Reading: chirality-emitted native code lands within 1.2x to 1.5x of gcc -O0 on
these kernels and 4x to 57x behind gcc -O2. The scaffold's tal interpreter
(the MET_TAL=1 engine) measures 2600 to 7800 ns per iteration on the same
kernels at small sizes, roughly 180x to 440x slower than the emitted code,
which is corroborating evidence that the native rows are machine code and
not interpretation.

## Reproduction and verification (second run, same day)

`sh run.sh` was run a second time on the same guest, and the -O2 disassembly
was read to answer the two questions a fast -O2 number should always face:
*was the kernel actually run, or did gcc delete or partially-evaluate it?*

**Ratios reproduce as a band; absolutes do not reproduce at all.**

| kernel | native/-O0 (run 1 → 2) | native/-O2 (run 1 → 2) | native abs ns (run 1 → 2) |
|---|---|---|---|
| arith   | 1.43× → 1.05× | 4.4× → 3.9×  | 16.7 → 24.0 (+44%) |
| bytesum | 1.47× → 1.43× | 56.6× → 71.6× | 14.5 → 25.8 (+78%) |
| states  | 1.19× → 1.52× | 24.0× → 31.2× | 17.5 → 31.8 (+82%) |

Absolute ns/iter moved 44–82% between two runs on the same machine on the same
day (the -O0 C side moved with it: arith -O0 11.7 → 23.0 ns), because this is a
shared virtualized guest with no CPU pinning or frequency control. **Do not
quote any absolute ns figure.** The native/-O0 ratio survives what the
absolutes do not — native and -O0 both keep every value in memory and every
call, so guest load slows them together and the ratio holds. Across both runs
every kernel landed in **1.0×–1.5× of gcc -O0**; that band, not any single
number inside it, is the claim. The -O2 gaps reproduce in magnitude
(single-digit× on compute-bound arith, tens× on the memory/branch kernels) but
not to two significant figures.

**The -O2 numbers are honest, confirmed by disassembly, not by trust.**

- *bytesum -O2 is a real scalar loop, not vectorized and not folded.* The inner
  loop (`c-O2-disasm.txt`, `main+0x570`) is exactly four instructions —
  `movzbl (%rax),%edx ; add $0x1,%rax ; add %rdx,%r8 ; cmp %rcx,%rax` — closed
  by `jne` back to the top, with the outer pass loop closing by `jne` beneath
  it. There is **no `psadbw`/`vpaddb`**, so the 56–72× gap is a genuine
  scalar-throughput gap (gcc's 4-instruction inlined loop vs chirality's call into
  `nb-bget` per byte), not SIMD and not fiction.
- *states -O2 keeps a real loop, not a folded constant.* 75 backward branches
  survive between the two bracketing `clock_gettime` calls; the state machine
  is inlined but iterated, not partially-evaluated to its result.
- *Anti-fold is structural, not incidental.* Inputs reach the kernel through
  `argv` (`atoll`, opaque to the compiler), the result lands in a
  `volatile int64_t sink` (`kernels.c:139`, defeating DCE) and is printed, and
  `report.py` asserts cross-side result equality — a deleted or wrong kernel
  fails the equality check, which passed both runs.

**Denominator.** Every ns figure is per innermost iteration of the k×n nested
loop: for arith one `(acc*3+i) mod` step; for bytesum one byte access (n = the
16 KiB buffer, so k×n counts each byte once per pass); for states one
state-machine step. Not per call, not per element-beyond-the-byte.

**Instructions-retired is owed, not measured.** `perf` / `perf_event_open` is
blocked in this microVM, so this benchmark reports wall-clock only and cannot
yet separate *"the emitter emits more work"* from *"the emitter emits the same
work but stalls"* — the two have different fixes (fewer instructions vs better
scheduling/regalloc). A `perf stat` run for cycles and instructions retired is
owed on bare metal, where absolute ns would also become quotable.

## Sixth run, same day: items 6+8 land -- a negative result, honestly read

Fused compare-and-branch (item 6) and the rax-residency peephole (item 8)
are in: the emitted artifact now contains **zero setcc** (every comparison
fuses to cmp+jcc) and **zero adjacent same-slot store->load pairs**
(disassembly-verified on this run's chirality-code.bin). Measured under
moderate load (noop 315 ns): ratios 1.85x / 7.6x / 10.2x vs -O2 --
statistically indistinguishable from run 5's 1.73x / 6.0x / 9.5x.

**Why verifiably tighter code did not move the wall clock:** these kernels
are latency-bound, not throughput-bound. arith serializes on the
imul -> idiv dependency chain (~26+ cycles of it per iteration); bytesum
on the loop-carried add + L1 load; states on its branch chain. The
instructions items 6+8 removed (guard setcc/movzx, bool round-trips, slot
reloads) were executing in the SHADOW of those chains on an out-of-order
core -- removing hidden work changes instruction count, not cycle count.
The reduction is real and matters where the shadow is absent (in-order or
narrow cores, code with independent work to schedule, icache pressure);
on these three kernels the next lever is the critical path itself:
**magic-multiply constant division** (arith's idiv -> ~3-cycle multiply
chain) is now the single highest-value remaining transform, followed by
real register allocation (shortens chains by removing store->load latency
from the dependency path, not just the instruction stream).

## Eighth run (2026-08-02): jump tables + peephole B -- convergence, honestly

Quiet guest (noop 150 ns; comparable to runs 5/7). Ratios vs -O2:

Two disassembly-verified findings the wall clock alone would hide:

- **Jump table: correct, not faster here.** jtb fired (the one indirect

  passes, but states' point estimate moved +3%: with per-iteration-varying

## 1. Execution-mode verification

What executes in each mode, established by reading the code and by direct
evidence from this run:

- chirality native (the timed side). scaffold/chirality/native.py
  (NativeBackend.compile) runs the chirality emitter (lib/emit-x64.chiral via
  emit-core/mach-x64) on the scaffold interpreter to produce machine-code
  bytes, maps a fresh read-write region through the chirality nb-sys-mmap
  crossing (native.py, _map_rw), copies the bytes in with ctypes.memmove,
  seals the code region read-execute through nb-sys-mprotect (compile, near
  the end), and wraps each entry offset in a ctypes.CFUNCTYPE over the raw
  address. A timed call is therefore a direct call into mmapped RX x86-64
  code; Python is the loader and the call trampoline only. This is the same
  path scaffold/tests/test_native.py exercises.
- MET_TAL=1 (not timed as native, and not native). scaffold/chirality/cli.py
  lowers eligible functions and hands them to tal.TalMachine, a Python
  dispatch loop over tal instructions (tal.py, TalMachine._block). It is a
  reference interpreter. It appears in the table as tal-interp, for scale,
  at small sizes only.
- The default `chirality run` mode is the upper-level Python evaluator, slower
  still; it is not part of this benchmark.

Direct evidence from this run, all reproduced by run.sh:

1. Differential check: before timing, each kernel is run at small sizes on
   both tal.TalMachine and the compiled entry point and the results are
   asserted equal (bench_native.py; the run prints CHECK,differential,pass).
2. Artifact disassembly: the emitted bytes are dumped to
   /tmp/chirality-bench/chirality-code.bin and disassembled with
   objdump -D -b binary -m i386:x86-64 into chirality-code-disasm.txt. The
   entry offsets printed by the driver (OFFSET lines) point at ordinary
   x86-64 prologues. arith-outer at offset 0x1d5 in this run:

       1d5: push   %rbp
       1d6: mov    %rsp,%rbp
       1d9: sub    $0x50,%rsp
       1e0: mov    %rdi,-0x8(%rbp)
       1e7: mov    %rsi,-0x10(%rbp)
       1ee: mov    %rdx,-0x18(%rbp)
       ...
       214: cmp    %rcx,%rax
       217: setg   %al
       ...

3. Scale: the tal-interp rows run the identical lowered tal functions at
   2600 to 7800 ns per iteration versus 14 to 18 ns natively. A Python
   interpreter cannot produce the native-row timings.
4. Result equality: the native results equal the C results for all three
   kernels at full size (report.py verifies this and prints
   "cross-side result equality: pass"), so the emitted code computed the
   same function.

## 2. Kernels

All three share one structural constraint: the chirality pure fragment has no
loop form and no mutation, and the emitter performs no tail-call
elimination, so loops are written as bounded-depth nested recursion (an
outer pass counter k over an inner loop of n iterations; peak stack depth
about k+n frames). The C sources are function-for-function transcriptions
of the chirality sources, recursion included. gcc is free to undo the recursion;
what each optimization level does with it is part of the measurement.

- arith (integer compute, k=5000, n=20000, 1.0e8 iterations):
  acc = (acc*3 + i) mod 1048573. The dependency chain runs through the mod.
  Plausibly bound by: division strategy. chirality emits a guarded
  cqo/idiv/cmovs sequence per mod (Euclidean semantics with divide-by-zero
  and INT_MIN/-1 guards, mach-x64.chiral x-mod-guarded); gcc -O0 emits raw
  idiv; gcc -O2 strength-reduces the constant mod to multiply/shift
  (visible in c-O2-disasm.txt: movabs of a magic constant, imul, sar).
  That strength reduction is most of the -O2 gap on this kernel.
- bytesum (memory walk, k=30000, n=16384, 4.9e8 nominal iterations):
  sum the bytes of a 16 KiB cell, k passes, pass start offset perturbed by
  k mod 7 so passes are not loop-invariant (the offset shaves at most 6
  elements per pass, under 0.01 percent; ns/iter uses nominal k*n). The
  16 KiB working set is L1-resident by design: the kernel measures
  per-element access machinery, not DRAM bandwidth. chirality compiles each
  bget to a call into the chirality-authored nb-bget (a one-load function, no
  bounds check at the machine level; the discipline is upstream), so an
  iteration is two calls (self-call plus nb-bget) with full frames. gcc -O2
  inlines bget and reduces the inner loop to four instructions
  (movzbl/add/add/cmp+jne, about 0.26 ns per byte). Plausibly bound by:
  call and frame machinery on the chirality side, pure L1 load throughput at
  -O2.
- states (branch/case heavy, k=20000, n=10000, 2.0e8 iterations): a five
  state machine driven by a 0,1,2 cycling counter; per iteration one case
  over the state (each arm casing the counter), a counter update function,
  and a state-to-code function. No division in the inner loop. chirality
  compiles case to a linear cmp/jne chain over immediate tags and each
  helper is a real call; gcc -O2 inlines everything and compiles the
  switches to branchless/jump code. Plausibly bound by: branch and call
  machinery.

Shared semantics kept identical by construction: all values non-negative,
so chirality Euclidean / and % agree with C truncated / and %; all
intermediates fit i64 with no overflow on either side (chirality native
arithmetic wraps at 64 bits, C signed overflow would be UB; neither is
reached); no allocation inside any timed region on either side (enum
states are immediate tags natively; the byte cell is allocated once in the
arena before timing, the C buffer once with malloc); no bounds checks on
either side; no GC on either side.

## 3. Method

- Timing: monotonic clock on both sides. C times inside the process with
  clock_gettime(CLOCK_MONOTONIC) around the kernel call only (no process
  startup, no argv parsing, no buffer fill). The native side is timed with
  time.perf_counter_ns around the single CFUNCTYPE invocation that performs
  the whole k*n region (no emitter, loader, or checker time is inside the
  timed region; compilation happens once, before timing).
- Reps: 2 warmup runs discarded, 5 measured reps per kernel per side.
  Tables report min, median, max. Raw per-rep numbers are below.
- Region size: every timed region on every side is over 100 ms (smallest:
  gcc -O2 bytesum, 122 ms min).
- Invocation overhead: the timed native region necessarily includes one
  Python-to-native call. Measured on a do-nothing kernel (noop, returns its
  argument): 179 ns per call, i.e. about 1e-7 of the smallest native
  region. Reported, not subtracted.
- Anti-folding: all kernel inputs reach C through argv at runtime; results
  flow into a volatile sink and are printed; report.py asserts result
  equality across sides, so a folded or wrong kernel cannot pass. The -O2
  disassembly was inspected: main contains the inlined kernel loops
  (backward branches present; the arith reciprocal-multiply loop and the
  four-instruction bytesum loop are visible in c-O2-disasm.txt, kept by
  run.sh).
- Interpreter rows: tal-interp times tal.TalMachine on the same lowered
  functions at the SMALL sizes from bench_sizes.py (1 warmup, 3 reps).
  Order-of-magnitude context only; not the same region size.
- Compiler: gcc (Debian 12.2.0-14+deb12u1) 12.2.0. Flags: exactly -O0 and
  -O2, no others. Python 3.11.2.

observed spreads in this run were gcc -O2 states (131 to 177 ms, about 30
percent, a short region in a virtualized guest) and one outlier rep each in
c-O0 bytesum and tal-interp bytesum.

## 5. Why the numbers look like this

The emitted code's register model explains the native-vs-C-O0 shape: every
tal register lives in a stack slot relative to rbp; every primitive loads
its operands into rax/rcx from slots, operates, and stores the result back
to a slot (see the disassembly snippet above, and mach-x64.chiral). gcc -O0
also keeps every C variable in memory and keeps all calls, which is why the
two land within 1.2x to 1.5x of each other. gcc -O2 then does what the
chirality emitter deliberately does not yet do: register allocation, inlining,
tail-call to loop conversion, and strength reduction. The 4x (division
bound), 24x (branch bound), and 57x (memory bound with a four-instruction
loop) gaps are those passes, applied kernel by kernel.

## 6. Environment and caveats

- Guest: KVM microVM (rootless podman + libkrun), Linux 6.12.91, Debian 12
  userland, 12 vCPUs. CPU model string is the generic
  "Intel(R) Xeon(R) Processor": the hypervisor masks the real model, so
  the microarchitecture is unknown here, and division/branch costs vary
  meaningfully across Intel generations. Absolute ns/iter numbers should
  not be quoted beyond this machine; the cross-side ratios are the
  defensible part.
- Virtualized timing: clock reads and scheduling pass through the
  hypervisor; no CPU pinning, no frequency control, other guest activity
  not excluded. The 100 ms floor and 5-rep min/median/max spread are the
  mitigation; the observed spread (above) bounds the jitter actually seen.
- The native side cannot yet run without Python in the process: Python
  hosts the emitter run, the loader, and the call-in trampoline. The timed
  region excludes all of it except the single 179 ns call crossing
  (measured, reported above).
- The loop shape (nested recursion, no TCO) is the chirality-idiomatic and
  stack-safe way to express these loops today, and the C sides transcribe
  it. A C programmer would write for-loops; at -O2 gcc effectively rewrites
  the recursion into exactly those loops, so the -O2 columns double as the
  for-loop baseline. At -O0 the C columns share the call-per-iteration
  cost with chirality.
- scaffold/chirality/optimize.py (a tal-level fold pass) exists but is not part
  of the NativeBackend path exercised here, matching test_native.py.
- Single machine, single day, gcc 12.2.0 only. reps=5, warm=2, seed=1 are
  set in run.sh; sizes in bench_sizes.py.

## 7. Files

- kernels.chiral: the three kernels plus noop, chirality surface syntax.
- kernels.c: the C transcription plus the timing driver.
- bench_native.py: emits/loads/checks/times the native side, times the tal
