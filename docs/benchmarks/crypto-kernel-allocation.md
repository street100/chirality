# What ChaCha20 costs, and what its inner loop allocates

`lib/crypto/chacha.chiral` is built and gated (`tools/test/run-tests.sh` phase
31). Its header comment at `:38-41` says *"Rounds allocate cells, never buffers,
which keeps the loop off the arena's Bytes path."* That sentence is true as
written. This file measures the half it leaves open: whether those cells survive
to runtime, and what they cost.

**Headline: they survive, and they are the majority of the cost.**

> Ten double rounds allocate **4,560 B in 90 arena cells per 64-byte block**,
> which is **71.25 B per keystream byte**, in the loop
> `crypto-primitives/K20` requires to allocate nothing. The whole block
> function allocates **5,776 B per block**. Keystream generation runs at
> **12.9 to 14.0 MB/s** at quiet load on the host below, **178 to 194 cycles
> per byte** at the reported clock. The same ARX arithmetic with the products
> removed runs **3.1 to 3.4x faster** at quiet load and **3.2 to 3.8x** under
> load, so the built kernel's per-byte time is what **110 to 133 ops/byte**
> would cost against a static count of **35**.

`crypto-primitives/K20`'s zero-allocation requirement, and arc requirement 5's
observable *"no allocation in an inner loop"*
(`docs/arcs/crypto-primitives-arc.md:113-115,143`), are **already violated by the
built kernel**. `K20` is `unminted` and `open`, so this is a measurement of the
gap it will have to close.

## The instrument

`heap-allocated` (`lib/ports/process.port:36`) reads `heapptr - heapbase`: the
arena's own bump cursor. The bump pointer only advances and nothing reclaims, so
the difference is **total bytes ever allocated, exactly**, and is the allocator's
own state. This is the counter
`docs/benchmarks/text-matcher-allocation.md:67-80` introduced after `memory.peak`
was measured to under-read the arena by 1.06% to 9.5% and to jitter between
identical runs. No figure here is a `memory.peak` reading, so no figure here is a
lower bound for that reason.

**What the counter establishes.** It counts bytes handed out by `x-alo` and
`x-galo` (`lib/lowering/x64/mach.chiral:483,515`), the only two allocation paths
a compiled program takes. A zero from it means no cell was constructed on the
measured path. It says nothing about stack traffic, register pressure or spill,
and this file measures none of those.

Two facts hold the readings together. Every per-iteration figure below is an
exact multiple of 1000 over 1000 iterations, bit-identical between runs. And the
arithmetic predicts them: `x-galo` allocates `sz = 8 * (1 + fields)`
(`mach.chiral:511`), so a `Q4` is 40 B and an `St` is 136 B, and the ladder falls
out of those two numbers with no residue.

## 1. The products survive. The backend does not unbox them

Three independent lines of evidence, all pointing the same way.

### 1a. The runtime counter, one stage per subject

Bytes allocated per iteration, 1000 iterations, key and nonce bound once and
threaded as parameters. Each row runs everything above it.

| subject | what it runs | B/iter | delta | what the delta is |
|---|---|---|---|---|
| `sI` | `block-init` | 136 | 136 | one `St` cell, `8*(1+16)` |
| `sR1` | `+ one double round` | 592 | **456** | 8 `Q4` at 40 B, plus one `St` at 136 B |
| `sD` | `+ ten double rounds` | 4,696 | **4,560** | 80 `Q4` plus 10 `St` |
| `sF` | `+ st-add` | 4,832 | 136 | one `St` cell |
| `sA` | `+ st-bytes`, the whole `chacha-block` | **5,776** | 944 | 16 `pack-u32` plus 15 `bcat` |
| `sB` | the ARX baseline, no product built | **0** | | |

The 456 B double round is `8 x 40 + 136` to the byte, and the ten-round figure
is exactly ten times it. **The predicted ~90 cells per block are all there**: 80
`Q4` and 10 `St`, 4,560 B, one cell per constructor application with nothing
elided.

The 944 B tail is the one Bytes-path cost in the block function, and it is
predicted too: a Bytes cell is 8 B of header plus its payload rounded to 8, so
`st-bytes` is `16 x 16` for the `pack-u32` results plus 688 B for the fifteen
`bcat` results at lengths 8 through 64, which is 944.

### 1b. The same code with the product removed allocates nothing

`sB` is `qround`'s body verbatim (`lib/crypto/chacha.chiral:50-56`), calling the
same `add32` and `rotl32` out of the same module, with the four lanes carried as
**parameters** across a self tail call instead of returned in a `Q4`. Over
8,000,000 quarter rounds it allocates **0 bytes**.

So the backend can hold four 32-bit lanes across a loop iteration with no cell.
It does not do so when the same four lanes leave a function inside a `Q4`. The
product is what forces the allocation.

### 1c. The emitted machine code, disassembled

`x-galo` emits `lea rcx,[rax+sz]` twice per allocation site
(`mach.chiral:513,519`). Counting that byte pattern in the block subject's ELF:

```
   lea rcx,[rax+ 40]  x2  = 1 allocation site(s)   Q4  4 fields
   lea rcx,[rax+136]  x6  = 3 allocation site(s)   St 16 fields
```

One `Q4` site and three `St` sites, matching the source exactly: one `(q4 …)`
in `qround`, and three `(st …)` in `block-init`, `dround` and `st-add`. Nothing
was unboxed at emission. The `Q4` site disassembles to 16 instructions on the
taken path:

```
mov  rax,QWORD PTR [rip+…]      ; heapptr
lea  rcx,[rax+0x28]             ; bump by 40
cmp  rcx,QWORD PTR [rip+…]      ; heapend
jbe  +7                         ; fits, commit
call …                          ; arena-grow, not taken
jmp  …
mov  QWORD PTR [rax],0x0        ; tag
mov  rcx,QWORD PTR [rbp-0x68]   ; \
mov  QWORD PTR [rax+0x8],rcx    ;  |
mov  rcx,QWORD PTR [rbp-0xa0]   ;  | four lanes copied out of
mov  QWORD PTR [rax+0x10],rcx   ;  | stack slots into the cell
mov  rcx,QWORD PTR [rbp-0x88]   ;  |
mov  QWORD PTR [rax+0x18],rcx   ;  |
mov  rcx,QWORD PTR [rbp-0x80]   ;  |
mov  QWORD PTR [rax+0x20],rcx   ; /
mov  QWORD PTR [rbp-0xa8],rax   ; the cell pointer into a slot
lea  rcx,[rax+0x28]
mov  QWORD PTR [rip+…],rcx      ; heapptr
```

The lanes arrive from `[rbp-…]` slots, so the round's live values are on the
stack before the cell is built, and the cell is a second copy of them.

**Caveat on 1c.** The static site count cannot distinguish a site that runs from
one that does not: both subjects import `crypto/chacha` and carry the same
emitted module. It is 1a and 1b that establish which sites execute. What 1c adds
is that no `Q4` or `St` construction was optimized away at emission, and what
one costs in instructions.

## 2. Throughput

`sA` generates 100,000 keystream blocks, 6,400,000 B, one `chacha-block` per
iteration on a climbing counter, one byte of each block folded into an
accumulator that is printed. `sB` runs 8,000,000 ARX quarter rounds, which is
**exactly the ARX work of those 100,000 blocks** (80 quarter rounds per block).
`sD` runs `block-init` plus ten double rounds, no feed-forward and no
serialization, so it carries the same 8,000,000 quarter rounds plus the cells.

Run-10 per pass, 2 warmups discarded, three passes. Seconds, min/median/max.
`/proc/loadavg` 0.16 to 0.61 at the start.

| pass | | `sB` ARX (0 B) | `sD` init+10dr | `sA` block |
|---|---|---|---|---|
| 1 | real | 0.142/**0.143**/0.147 | 0.323/**0.328**/0.343 | 0.478/**0.483**/0.494 |
| 2 | real | 0.143/**0.146**/0.149 | 0.328/**0.333**/0.346 | 0.479/**0.484**/0.497 |
| 3 | real | 0.144/**0.147**/0.158 | 0.322/**0.324**/0.337 | 0.480/**0.485**/0.492 |
| 1 | user / sys | 0.142 / 0.000 | 0.228 / 0.095 | 0.358 / 0.120 |
| 2 | user / sys | 0.145 / 0.000 | 0.220 / 0.103 | 0.356 / 0.120 |
| 3 | user / sys | 0.147 / 0.000 | 0.217 / 0.097 | 0.346 / 0.135 |

An earlier 30-run set on equivalent binaries the same day, at `/proc/loadavg`
0.16, put `sA` at medians 0.466 to 0.468 (min 0.456, max 0.511), `sB` at 0.146
to 0.149 (min 0.141), `sD` at 0.318 to 0.328 (min 0.313). Those two sets are the
**quiet-load** measurement.

A **third** 30-run set came from `crypto-kernel.sh` with no argument, which runs
all four passes back to back and raises the load on itself. It put `sA` at
medians 0.553 / 0.553 / 0.551 (min 0.488, max 0.650), `sB` at 0.145 / 0.172 /
0.174, `sD` at 0.333 / 0.380 / 0.384. Its matched-pass `sA`/`sB` ratios are
3.81, 3.21 and 3.17. The 3.81 is a pass whose baseline ran before the load rose
and whose subject ran after, so it is the widest sample and the least
comparable one. It is quoted anyway, because the honest-spread rule in
`docs/benchmarks/README.md` makes the band the claim.

| | quiet load, 60 runs | all three sets, 90 runs |
|---|---|---|
| keystream throughput | **12.9 to 14.0 MB/s** | 9.8 to 14.0 MB/s |
| per byte | **71.3 to 77.7 ns** | 71.3 to 101.6 ns |
| cycles per byte at the reported 2496 MHz | **178 to 194** | 178 to 254 |
| `sA` / `sB`, wall clock, matched pass | **3.1 to 3.4x** | 3.1 to 3.8x |
| `sD` / `sB`, wall clock, matched pass | **2.2 to 2.3x** | 2.2 to 2.3x |
| `sA` / `sB`, user time only, matched pass | **2.2 to 2.5x** | 2.2 to 2.9x |

**Quote the quiet-load column.** `docs/benchmarks/language-performance.md`
settles this shape: on a shared virtualized guest with no CPU pinning the
quiet-versus-quiet runs are the directly comparable ones, and the loaded column
is the wobble. `sD`/`sB` is the one ratio that held across every set.

⚑ **The cycles-per-byte figure is a conversion.** No cycle counter was read.
`perf` and `perf_event_open` are blocked in this microVM, which
`docs/benchmarks/language-performance.md` already records as an owed
measurement. The number is wall clock divided by the `cpu MHz` the guest
reports. Turbo, throttling and the host's own scheduling are all outside it. The
ratios and the MB/s are the defensible part.

⚑ **A quarter of `sA`'s wall clock is kernel time.** `sys` runs 0.120 to 0.135
of a 0.484 s median, faulting in the 578 MB of fresh arena the run allocates and
never reuses. A runtime that reclaimed would not pay that. The **user-time
ratio, 2.2 to 2.5x, is therefore the lower bound** on the cell cost, and the
3.1 to 3.4x wall-clock ratio is what this runtime actually charges.

## 3. The gap against 35 ops/byte

The static count is 2,240 ops per 64-byte block: `qround` is
`4 x (add32=2, bxor=1, rotl32=4)` = 28 ops, 80 quarter rounds per block, so
**35 ops/byte**.

`sB` executes exactly that op count and op mix with no product. On this machine
it costs **55 to 58 cycles/byte**, which is **1.6 cycles per op**. That is what
35 ops/byte is worth here: the ARX chain is serial, each result feeding the
next, so it does not retire at one op per cycle.

The built kernel costs **178 to 194 cycles/byte** at quiet load. Divided by the
baseline's own 1.6 cycles per op, its per-byte time is what **110 to 120
ops/byte** would cost, and 133 ops/byte at the loaded set's widest sample.

| | ops/byte | cycles/byte, quiet load |
|---|---|---|
| static count, hand-verified | 35 | |
| `sB`, that count with no product built | 35 | 55 to 58 |
| `sD`, plus the 90 cells of `rounds` | 35 | 124 to 130 |
| `sA`, the whole block function | 35 | 178 to 194 |
| `sA` expressed at the baseline's rate | **110 to 120** | |

**The static count under-predicts by 3.1 to 3.4x**, and about two thirds of the
excess is inside `rounds`. Every projection built on 35 ops/byte should be
divided by that factor until `K20` closes.

Where the excess sits, from 1a and 1c: 90 cells per block at 16 instructions
each for a `Q4` and 40 for an `St`, the field reads that take the lanes back out
of those cells, the stack slots the lanes occupy before each cell is built, and
5,776 B per block of arena that is written once and never read again.

### Against the tree's measured bands

`docs/benchmarks/language-performance.md` puts chirality at ~1.4x of `gcc -O2`
on compute and 5 to 8x on memory and branch work. **This file's 3.1 to 3.4x is
not comparable to those figures**, because its denominator is an in-tree
non-allocating chirality kernel and theirs is `gcc -O2`. A `gcc -O2` ChaCha20
comparison was **not run** and no number here should be read as one.

What the ratio does establish is direction. The ARX baseline is a compute
kernel. The built cipher spends more than three times as long as its own
compute shape, and spends it on cell construction, field reads and arena
traffic, which
is the work the 5 to 8x band names. The kernel sits between the two bands and is
being pulled toward the slower one by the products.

## The stream path is worse, and it is quadratic

`chacha-xor` is the exported stream encrypt. `cx-blocks`
(`lib/crypto/chacha.chiral:153-157`) appends each block's output to a growing
accumulator with one `bcat`, so the accumulator is copied once per block. One
call per process run, run-10 each:

| message B | allocated B | B per message byte | real min/med/max | MB/s |
|---|---|---|---|---|
| 16,384 | 4,837,824 | 295 | 0.008/0.009/0.012 | 1.8 |
| 32,768 | 13,869,504 | 423 | 0.025/0.025/0.027 | 1.3 |
| 65,536 | 44,515,776 | 679 | 0.085/0.086/0.092 | 0.76 |
| 131,072 | 156,139,968 | 1,191 | 0.315/0.317/0.323 | 0.41 |

Allocation grows 2.87x, 3.21x and 3.51x per doubling, time grows 2.8x, 3.4x and
3.7x, and both climb toward the 4x a quadratic gives.

The accumulator's own cost is predictable: a Bytes cell is 8 B of header plus
its payload rounded to 8, and the `m`-th `bcat` copies `64m` bytes, so `m`
blocks cost `8m + 32m(m+1)`. Subtracting that from the measured totals leaves
**exactly 10,664 B per 64-byte block** at both 65,536 and 131,072 (10,665 at the
two smaller sizes). Against `chacha-block`'s 5,776, `cx-run`'s per-byte `cc-b1`
and `bcat` add **4,888 B per block** on top of the keystream, before the
quadratic term touches anything.

The source comment at `:136-141` names the accumulator design and calls the
per-byte `bcat` on the whole message "the named anti-pattern". The block-local
`bcat` it chose instead is bounded, and the whole-accumulator `bcat` it kept is
the quadratic term measured here.

## What this does not establish

- **This is ChaCha20's state, which is 16 words. Keccak-f's is 25.** The
  allocation finding transfers directly, because it is about products surviving
  as cells and not about how many lanes fit in registers. The **register
  pressure finding does not**: 16 lanes plus four working values already spill
  to stack slots here (1c), so this is a **lower bound** on what a 25-lane
  permutation will face. Nothing here predicts Keccak's number.
- **No cycle counts.** `perf` is blocked in this microVM. Cycles per byte is
  wall clock against the guest's reported 2496 MHz.
- **No `gcc` comparison.** The baseline is in-tree.
- **No spill or register-pressure measurement.** 1c shows lanes arriving from
  stack slots at one allocation site. Counting spills across the kernel was not
  attempted.
- **No claim about `x-alo` against `x-galo`.** The counter does not separate the
  trapping allocator from the growing one, and the split stands unmeasured.
- **The 1.6 cycles per op is this machine's rate for this op mix**, measured
  from `sB`. Reading it as a general figure for chirality codegen would be wrong.

## One thing found while instrumenting

A top-level `(def name Bytes …)` is **re-evaluated at every reference**.
Measured in isolation over 1000 references: the 32-byte key built from eight `pack-u32`
and seven `bcat` costs **336 B per reference**, the 12-byte nonce **88 B**. A
first pass at this benchmark charged 424 B per block to the kernel for that
reason. Every subject in the driver binds key and nonce once and threads them as
parameters, and the corrected block figure is 5,776 B against the 6,200 B the
uncorrected driver reported. This is a property of the driver's own defs and is
not a finding about `lib/crypto/chacha.chiral`, which takes both as arguments.
